# Sidecar Capabilities Flag

**Source:** [Provider Ports](../architecture/provider-ports.md#not-built-here-and-where-it-went) P15/#696's "Not built here" table ("a `--capabilities` flag on each sidecar so the host learns an engine's runtime capability instead of from a static descriptor and the existing probes... No PRD yet"); the owner has since said the un-PRD'd Coulds are wanted work (#509, 2026-09-27). This PRD fills that row.

**Tracking:** [#712](https://github.com/countrymanprime/narration-utils/issues/712).

## Problem Statement

`ProviderCapabilities()` (`apps/desktop/bindings_providers.go:24-26`) tells the UI what a sidecar's registries declare — but it reads that from **Go's own static registry rows** (`asrport.Engines`, `ttsport.Engines`, `pronunciationport.Sources`, `captureport.Backends`), never from the sidecar process itself. The Decisions Log says so directly: "Go learns a Python engine's capability from a static descriptor plus the probes that exist, not from asking the sidecar" (`docs/architecture/provider-ports.md:83`). That is accurate for what ships today — Windows-only, one frozen build per platform — but it means the Go-side answer and the Python-side reality can silently diverge: a row can be declared in `asrport.Engines` (compiled into every build, unconditionally) while the adapter that fills the matching Python row fails to import in a given process (a missing native library, a frozen build that lost a DLL — the exact class of failure `--check-moonshine` exists to catch, one engine at a time, one platform at a time, one sidecar at a time). There is no generic, sidecar-reported "here is what I actually have registered right now" answer; each such answer today is a bespoke, single-purpose flag.

## Evidence

- **The only existing precedent is single-purpose and manually wired.** `--check-moonshine` (`sidecars/manuscript-teleprompter/core/live_asr.py:761-765`) exists solely "to check the frozen Teleprompter sidecar can load Moonshine's native library... which PyInstaller cannot see it needs" (`apps/desktop/smoke.go:35-36`). It answers one engine, one sidecar, one report shape (`moonshine_engine.py`'s `self_check()`, whose report is `{"type": "engine_check", "engine": "moonshine", "ok": bool, "detail": str}`, consumed by a hand-written Go struct `moonshineCheckReport` in `smoke.go:308-313`). Adding a second engine that needs the same kind of check today means writing a second flag, a second report shape, and a second Go parser — there is no reusable pattern, only one instance to copy.
- **The registries already carry everything a generic report needs, because the guard already reads them the same way.** `libs/python/tests/test_provider_guard.py` "reads the provider names from the adapters' own `descriptor = …Descriptor(…)` declarations" (`provider-ports.md:49`) — the exact data a `--capabilities` flag would enumerate (name, label, platforms, modes, asset kind) already exists on every registered row's `Descriptor` (`libs/python/narration_common/ports/registry.py`'s `Descriptor`, referenced throughout `provider-ports.md:30-33`). No new metadata needs inventing; a `--capabilities` flag is a serializer over data the guard already walks.
- **Each sidecar is its own process with its own registry contents, which the host cannot see any other way.** `provider-ports.md:26`: "Each sidecar is its own process, so the teleprompter's live `whisper` row and transcript compare's batch `whisper` row never share a registry." Nothing today lets the host ask "what did *this* process actually manage to import and register", as opposed to "what does the source code declare should be there" (the Go side) — the gap `ProviderCapabilities`'s own module comment flags as future work ("a later PRD may use it to explain a disabled choice... the way `DawCapabilities` explains a disabled DAW control", `bindings_providers.go:17`) without closing it.
- **The three sidecars have two different CLI shapes, which the flag must fit without forcing a rewrite.** `manuscript-teleprompter`'s entry (`sidecars/manuscript-teleprompter/core/live_asr.py`) is flag-style: `build_parser()` returns one `argparse.ArgumentParser` with `--check-moonshine`, `--list-devices`, `--meter` etc. as mutually-exclusive-in-practice boolean flags checked in sequence inside `main()` before the "real" work (`live_asr.py:830-855`: `if args.check_moonshine: ...; return`). `manuscript-guide`'s entry (`sidecars/manuscript-guide/core/manuscript_guide.py`) is subcommand-style: `command.add_parser("self-check", ...)` alongside `build`, `status`, `edit`, `rescan` (`manuscript_guide.py:1252-1312`) — self-check is a *subcommand*, not a flag. `transcript-compare`'s entry (`core/compare.py`/`core/take_divergence_mode.py`) has its own shape again. A single `--capabilities` design that only works for one CLI shape would need the very flag-vs-subcommand rewrite the owner has given no evidence of wanting; see Open Questions Q1.
- **The wire shape to mirror already exists, host-side.** `providerCapabilitiesPayload` (`apps/desktop/bindings_providers.go:32-62`) already defines the exact JSON shape a sidecar-reported answer should echo: `{platform, asr: {<name>: {label, default, platforms, modes, asset?, support}}, tts: {...}, pronunciation: {...}, capture: {...}}`. A sidecar's `--capabilities` output does not need a new shape invented from nothing — it needs the same per-port, per-row shape, minus the two things only Go's registry (compiled into every build) can answer for a process that hasn't even started yet: `default` (Go's `captureport.For(platform)`-style "first row for this platform" logic) and `support` (a platform-availability judgment `ProviderSupport` makes without running anything). A sidecar instead reports **what it has actually registered in this process**, which is a strict subset question: present/absent per row, plus whatever each row's own `descriptor` carries.
- **This is a diagnostic tool, not a wire contract.** `smoke.go`'s own package comment frames `--check-moonshine` as part of "the packaged-app smoke test" — a CI/release-verification tool, not something a live UI screen binds to. `--capabilities`, generalizing that pattern, is the same kind of tool: consumed by `smoke.go` (replacing or supplementing the Moonshine-only check) and by a human running the sidecar directly to debug a frozen build, not by `apps/ui`. This keeps it **outside** the wire-contracts discipline `CLAUDE.md` requires for anything "the host reads back from disk" as a UI-facing binding result — this is stdout JSON a Go test/tool parses, the same category `moonshineCheckReport` already is, not a Zod-schema'd binding.

## Proposed Solution

Add a `--capabilities` flag (or, where the sidecar's CLI is subcommand-style, a `capabilities` subcommand — Q1) to each of the three sidecars, printing one JSON report of every provider port row that sidecar's process has actually registered by the time the flag is handled — after every adapter-registering import has run, before any engine, model, or device is touched. The report's shape generalizes `providerCapabilitiesPayload`'s per-row fields (name, label, platforms, modes, asset kind) minus the two host-only judgments (`default`, `support`), plus one field only a live process can answer: whether the row's adapter actually imported cleanly (mirroring what `--check-moonshine` proves for Moonshine alone today, generalized to every row instead of one hardcoded engine).

Consume it from `apps/desktop/smoke.go`, generalizing `checkFrozenMoonshine` into a `checkCapabilities` (or replacing it outright — Q4) that compares each sidecar's self-report against the platform-appropriate subset of the Go-side static registries, and fails the smoke test if a row Go declares for this platform is missing from the sidecar's own report (the exact class of freeze-silently-loses-a-native-library bug `--check-moonshine` exists to catch today, generalized past Moonshine).

This does **not** replace `ProviderCapabilities()` or change what the UI sees — `bindings_providers.go` keeps reading the static Go registries, unchanged (Decisions Log entry below explains why).

## Key Hypothesis

We believe one generic `--capabilities` report, generalizing `--check-moonshine`'s "does this row actually work in this process" question to every registered provider row instead of one hardcoded engine, is enough to let the packaged-app smoke test catch a freeze silently losing *any* engine's native dependency — not just Moonshine's — with no new bespoke flag needed the next time a provider gains a native runtime dependency. We'll know we're right when a fault injected into a non-Moonshine adapter's import (deliberately broken in a test, mirroring how the guard's own fixtures deliberately break things to prove they fire) is caught by `checkCapabilities` the same way a broken Moonshine import is caught today.

## What We're NOT Building

- A UI-facing binding or wire contract. This is a CLI diagnostic flag, consumed by `smoke.go` and by a human running a sidecar directly — not by `apps/ui`, not schema'd in `apps/ui/src/api/schemas/`, not a `wireContracts.test.ts` row. If a future PRD wants the UI to show *live* per-process capability instead of the static `ProviderCapabilities` answer, that is a new, separate wire-contract proposal built on top of this flag's output — out of scope here.
- Replacing `ProviderCapabilities()` or changing its payload, its callers, or its `hostAPIVersion`. See the Decisions Log for why Go keeps reading static registries even after this ships.
- A generic plugin-loading or capability-negotiation protocol between Go and Python. The provider-ports Decisions Log already rejected "Python ports are... plain registries filled at import, not ABCs or entry-point plugins... plugins would widen the trust boundary" (`provider-ports.md:86`); this PRD reports on what already registered, it does not change how or when registration happens.
- Rewriting any sidecar's CLI from subcommand-style to flag-style or vice versa, purely to make `--capabilities` uniform. Q1 recommends fitting each sidecar's existing shape instead.
- Per-model or per-voice capability detail (which Whisper model sizes are downloaded, which Piper voices are installed) — that is `ProviderCapabilities`'s `asset.installed` counter's job today (`bindings_providers.go:74-79`) and stays host-side, reading the asset catalog, not the sidecar.

## Open Questions

- [ ] **Q1. Flag or subcommand, per sidecar's existing shape?** `manuscript-teleprompter` is flag-style (`--capabilities`, mirroring `--check-moonshine`); `manuscript-guide` is subcommand-style (`capabilities` alongside `build`/`status`/`edit`/`rescan`/`self-check`). Recommendation: fit each sidecar's existing CLI shape rather than forcing uniformity — `manuscript-teleprompter` gets `--capabilities` as a flag (Phase 1), `manuscript-guide` gets a `capabilities` subcommand (Phase 2), `transcript-compare`'s shape is decided when its phase is implemented (check its current entry point then; it changes less often than the other two). `smoke.go`'s `checkCapabilities` handles the CLI-shape difference at the call site, the same way `checkFrozenMoonshine` today already knows to pass `--check-moonshine` as a flag, not a subcommand — this is a small, contained difference, not architectural inconsistency.
- [ ] **Q2. Does `--capabilities` attempt to *load* each engine (proving it truly works, like `--check-moonshine` does for Moonshine's native library) or only report what *imported and registered* (a weaker, faster check)?** Recommendation: report registration only by default (fast, no side effects, safe to run against every row including ones needing a large model file) with each row noting `"loadable": null` when untested; a future, separate flag or a `--capabilities --verify` extension could opt into per-row load checks (mirrors `--check-moonshine`'s heavier "load the native library" check) — but that is real added scope (each engine's load path differs, some need a model file this diagnostic shouldn't require) and should not be assumed as Phase 1/2 scope without the owner confirming it's worth the cost. Recorded as the shape decision in [ADR 0403](../adr/0403-the-capabilities-flag-reports-what-registered-not-what-loads.md) (Proposed).
- [ ] **Q3. Does `checkCapabilities` in `smoke.go` fully replace `checkFrozenMoonshine`, or run alongside it?** Recommendation: replace it once `--capabilities` reports registration for the `moonshine` row *and* Phase 1 also folds in a `--capabilities --verify`-style native-library check for at least that one row (matching today's guarantee exactly) — otherwise replacing loses a real check `--check-moonshine` currently makes (Moonshine's DLL actually loads) that a registration-only report (Q2's default) would not catch. If Q2's "report only" default ships without a verify mode, keep `--check-moonshine` standing alongside the new generic flag rather than deleting a real safety check to simplify `smoke.go`. This is why Phase 3 (folding Moonshine's check into the generic flag) is `Depends` on Q2's resolution, not bundled into Phase 1.
- [ ] **Q4. Should the generic report also become the loading mechanism for a to-be-built `ProviderCapabilities`-freshness check (comparing Go's static answer against a sidecar's live one at app startup or `--smoke` time), or does it stay `smoke.go`-only for now?** Recommendation: `smoke.go`-only for this PRD (the evidence for the freeze-losing-a-dependency problem is concrete and scoped; a live startup cross-check is speculative scope creep with no stated narrator problem behind it) — a future PRD can propose the startup check if the owner wants it, building on this one's report shape rather than re-inventing it.
- [ ] **Q5. Priority relative to the rest of the deferred/Could queue.** Recommendation: filler-tier, same framing as this PRD's sibling ([CoreAudio Capture](coreaudio-capture.prd.md)) — not scheduled ahead of any wave, per the [agent train queue](../operations/agent-train.md#queue)'s "Filler" row.

## Users & Context

**Primary User**: the release-verification pipeline (`narration-utils --smoke`) and, secondarily, the owner or a future contributor debugging a frozen build where a provider silently doesn't work.
**Current behavior**: `smoke.go` can only ask "does Moonshine's native library load" (one hardcoded engine, one hardcoded sidecar); every other provider's runtime health in a frozen build is unverified by the smoke test.
**Trigger**: running `narration-utils --smoke` in CI or before a release; or a developer manually running a sidecar with `--capabilities` to debug "why doesn't this engine work in this build."
**Success state**: the smoke test catches a broken adapter import for *any* registered provider, not just Moonshine, before it ships; a developer gets a one-command answer instead of reading sidecar logs.
**Job to Be Done**: When I ship a frozen build, I want to know every declared provider actually works in it, not just the one engine someone remembered to write a check for.
**Non-Users**: the narrator-facing UI (this flag is never bound to a screen — see What We're NOT Building).

## Technical Approach

**Feasibility**: HIGH. Every piece of data the report needs already exists on registered rows' `Descriptor`s, already walked the same way by the provider guard; the only genuinely new code is the JSON serialization, the CLI wiring per sidecar (small, `argparse` additions matching existing patterns), and `smoke.go`'s comparison logic (a straightforward set-difference against the Go-side registries, no new dependency).

**Architecture notes**

- **The report iterates each sidecar's own registries directly** (`ENGINES`, `BACKENDS`, `SOURCES` per `provider-ports.md:9-15`'s table) — no new abstraction, no shared "capabilities" module across sidecars is needed or proposed, since each sidecar already imports only the adapters relevant to it (`provider-ports.md:19-24`'s adapter-module table).
- **Emission reuses each sidecar's existing `_emit`/`print(json.dumps(...))` pattern** (`live_asr.py`'s `_emit`, `manuscript_guide.py`'s `self_check`'s `print(json.dumps(...))`) — no new output channel.
- **`smoke.go`'s comparison logic is new but small**: for each port, take the platform-applicable subset of the Go static registry's `.Names(platform)` (already exists: `provider-ports.md:30`, `Names(platform)` lists rows declared for a platform), and check every name appears in the sidecar's reported rows for that port. This generalizes `checkFrozenMoonshine`'s single hardcoded `parsed.Engine != "moonshine"` comparison (`smoke.go:331`) into a loop over registries `smoke.go` already imports transitively through the port packages.
- **The provider guard needs no change.** `providerguard_test.go`'s one documented exception, `checkFrozenMoonshine`, "checks the frozen sidecar's `--check-moonshine` report names the engine it was asked about; it selects nothing" (`provider-ports.md:48`, `providerguard_test.go:29`) — the generalized `checkCapabilities` does the same kind of comparison (matching reported names against registry names, not choosing behavior based on a name), so it is the same guard exception, generalized, not a new one. The Python guard's two existing exceptions (`devices.py`, `locate.py`) are unaffected; if `--capabilities`' own code in each `core/*.py` entry needs to *list* provider names to build its report (not compare them to select behavior), confirm at implementation time whether that trips the Python guard's comparison patterns (`==`, `in`, a literal list) — iterating `ENGINES.entries()` to serialize should not, since it inspects rows generically rather than naming one.
