# DAW Integration Boundary

**Status: native Wails desktop workspace and REAPER file bridge implemented.**

## REAPER rules

- Keep business logic in Go and user-facing UI in React. The two packaged Python analysis sidecars remain Manuscript Guide and Transcript Compare. Keep only project discovery, manifest construction, marker/take mutations, and cursor navigation in REAPER Lua.
- Reading a project's track and item metadata does not need REAPER at all: the Go `tracks` package parses the `.rpp` file directly, so the [Tracks](../utilities/tracks.md) list in the audio engine panel works in a standalone launch. The "project discovery in Lua" rule above applies to state only a running REAPER knows (selection, edit cursor, take markers); anything derivable from the saved project file stays in Go.
- The installed launcher resolves its adjacent Wails executable and resource bridge; checkout paths are a development-only fallback.
- The launcher does not read or write ExtState paths. Go resolves the shared layered JSON settings and passes explicit marker colors with the marker-export command.
- Import `NarrationStudio_Launcher.lua` into REAPER's Action list. It starts the non-blocking native Wails workspace and its file-session bridge for REAPER-only operations. There is no loopback server, REST endpoint, browser tab, or port override.
- The workspace is a native Wails window. REAPER launches the executable directly; it does not use a loopback port, REST endpoint, browser tab, or port override.
- For new work, carry REAPER project, track, item, and take GUIDs in the shared finding record; use project-time ranges only as fallbacks.
- The bridge's protocol, commands, reachability heartbeat and test harness are in [the REAPER bridge](reaper-bridge.md). Going to and looping a finding by GUID, with the stale rule and how Stop restores the narrator's time selection and repeat, is in [going to and looping a finding](reaper-navigation.md).
- The app can locate and start `reaper.exe` itself: `apps/desktop/internal/daw.LocateReaperExecutable` reads the Windows Uninstall registry key (falling back to the `.rpp` file association), `daw.Resolve` lets a `DAW.reaper_path` Settings override always win, and `daw.Launch` starts it detached - never through the sidecar supervisor's kill-on-close job object, so REAPER outlives the app. The `Host.DawLaunch` binding passes the current project's linked `.rpp`, plus `NarrationStudio_Launcher.lua` as a trailing script argument when the `DAW.auto_start_launcher` Settings toggle is on (an owner decision; default off): REAPER 6.80+ auto-runs a script argument at startup with the project already open, confirmed on a real REAPER 7.80 ([spike S6](../research/reaper-spike-s6-daw-reachability.md), [locate.go](../../apps/desktop/internal/daw/locate.go)).
- The project's engine is a per-project choice, not the launch's alone (`dawport.ProjectKind`, `apps/desktop/projectdaw.go`). A `--daw` label overrides it while that launch runs. Otherwise it comes from the project's `Recording.engine` row, which Settings > Recording saves through `DawChoose`. With no row it comes from the folder: a linked `.rpp` or any `.rpp` directly in the folder means REAPER. Otherwise it is the built-in recorder where it runs. A Start-menu launch of a folder holding a REAPER project is therefore REAPER's, and the capability report, the record path and the Booth's setup chip follow it with no flag. `DawChoice` lists REAPER, Audacity and the built-in recorder with whether each was found and its record capability. `DawLinkFound` links the one `.rpp` the host found. The bridge still connects only when REAPER runs `NarrationStudio_Launcher.lua`: Start REAPER passes it only with `DAW.auto_start_launcher` on, and Settings > Recording says so.
- Manuscript line identity is stored on items as namespaced extension data and read back through the bridge; see [manuscript-line-identity.md](manuscript-line-identity.md) and [Manuscript line identity in the REAPER project](manuscript-line-identity.md).
- All mutation actions must be explicitly triggered by the narrator, wrapped in REAPER undo blocks, and report failures without partially applying unrelated actions. Transcript Compare therefore inspects take markers after analysis and only writes its pending findings when the narrator selects **Export markers**.
- Before export, the REAPER adapter marks a finding as already marked when the same active take has a marker within 0.15 seconds with the same case-insensitive issue prefix (`MISREAD:`, `SKIPPED:`, or `EXTRA:`). Export rechecks immediately before every add and reports added and skipped counts. Proof's marker for one finding (`add_finding_marker`, [adding the approved marker](reaper-navigation.md#adding-the-approved-marker)) uses the same rule (`existing_take_marker` in `narration_bridge_core.lua`) and the same name, in one undo block.

## Settings layering

Every user setting is resolved by the Go host through the same layered rules against the same on-disk JSON files, not REAPER ExtState. The Python sidecars receive their settings through their explicit command contracts. Three tiers, most-specific first:

1. Project override - `<project folder>/narration-utils/settings.json` (see Project-sidecar rules below).
2. Per-user global - `%APPDATA%/narration-utils/global-settings.json`.
3. Repo default - `config/defaults.json`, checked in.

REAPER never parses this JSON. The Wails host owns setting resolution and passes marker colors with the explicit marker-export command.

## Project-sidecar rules

- Store generated, reviewable metadata beside the `.rpp` project in a tool-specific folder.
- Do not rewrite source media or make user choices in place. Keep analyzer output, decision state, and cache data distinct.
- Use `<project>/narration-utils/manuscript/manuscript.json` as the common manuscript input. Source DOCX, Markdown, plain-text and EPUB files are copied into the manuscript source folder at explicit import time; runtime tools never parse them. Existing canonical PDF-derived v1 data remains readable, but new PDF import is fail-closed pending corpus parity.
- A project's settings overrides live in one shared sidecar, `<project>/narration-utils/settings.json` (sectioned by tool name), separate from each tool's own generated-output folder - it holds user-set overrides, not analyzer output.
- Findings (the shared record every analyzer emits, [findings-contract.md](findings-contract.md)) live under `<project>/narration-utils/findings/`: one regenerated JSON file per analyzer and scope, plus one shared append-only `review.json` decision history. Only the Go host writes there; `resetDerived` clears the whole folder when the manuscript it is anchored to is replaced or cleared.
- Analysis evidence ([fingerprint.go](../../apps/desktop/internal/evidence/fingerprint.go)) lives under `<project>/narration-utils/analysis/`: `ledger/` (one record per analyzer run), `cache/` (per-source results such as transcript words) and `coverage/` (the recording coverage service's stored results and, while a check runs, its working folder, [Recording Check (recording coverage)](../utilities/recording-coverage.md)); the confirmed track-to-chapter links are `<project>/narration-utils/chapter-track-map.json`. All of it is derived from the saved `.rpp`, never live REAPER state, and `resetDerived` clears it with the findings.
- The narrator's answers to chapter stage suggestions (confirm, dismiss, revert) are an append-only list in `<project>/narration-utils/stage-decisions.json`, keyed by the manuscript's `documentId` and kept beside the chapter status in `manuscript-notes.json`, never inside it ([stage recommendations](stage-recommendations.md#the-narrators-decisions), [The narrator's decisions](stage-recommendations.md#the-narrators-decisions)). A file kept for another `documentId` reads as empty, and `resetDerived` deletes it.
- The Booth's passage map, where each take of a recording began in the text and the item and take ids the DAW gave it, is `<project>/narration-utils/passagemap.json` ([the passage map](manuscript-teleprompter.md#the-passage-map)). Only the Go host writes it and stamps the ids; `resetDerived` deletes it.

## Audacity boundary

- Audacity is its own adapter, not a Lua port. Its closest finding representation is a UTF-8 label track. The layered Python config module and React workspace are DAW-agnostic, so an Audacity adapter reuses them directly.
- Use its optional `mod-script-pipe` only from a local desktop process and only after the user has enabled it.
- **Driven over `mod-script-pipe`, built from the published spec**. `apps/desktop/internal/audacitybridge` is the pipe client: the two fixed Windows named pipes, guarded commands that refuse what the syntax cannot carry, a strict reply parser, a 5 s timeout with reconnect, and a fake pipe server (`audacitybridgetest`) for tests. `apps/desktop/internal/dawport/audacity` declares `navigate`, `markers` and `macro_render` Experimental (the last is the mastering port's `audacity` row, [`macro_render`](../reference/daw/capabilities.md#macro_render)) and its `Session` carries the label import, read-back, mark-reviewed and chapter export; everything else keeps the [Audacity boundary](#audacity-boundary)'s "not available yet". Audacity 4.0 has no scripting interface ([spec research](../research/audacity-4-scripting-spec.md)), so there the adapter reports "not reachable"; Audacity 3.x with the module enabled is what the owner's [verification pass](../operations/audacity-verification-pass.md) checks. No page opens the pipe yet: Proof's DAW actions follow the capabilities (below), and there is no label import/export UI.
- **The launcher is a Start Menu entry, not an Audacity artifact**. Nothing Audacity loads can start a program: no macro or scripting command does it, and Audacity compiles Nyquist's `system` as a stub. So the installer's "Narration Studio for Audacity" entry starts `narration-utils.exe` with exactly `--daw Audacity`, and the narrator picks the project in the app. `ProjectSwitch` keeps an Audacity launch's label, where every other launch becomes `Standalone` (`pickerSwitchDAW`, `apps/desktop/bindings.go`), so the picked project opens with the Audacity adapter. No Audacity-side file ships, and `scripts/release/installer.test.mjs` pins the entry.
- **Nothing moves Audacity or changes its project unless the narrator asked.** Every command comes from a role method a narrator action calls. The adapter adds a label only for an approved finding and never removes one, rewrites only labels whose text carries its own `[nu:<id>]` identity, and matches them by that identity, never by time; a label the narrator hand-edits to carry another finding's identity is treated as that finding's. Capabilities stay Experimental, off unless the narrator turns them on, until the owner's pass.
- First adapter scope: import findings as labels, navigate/export reviewed labels, and preserve the DAW-neutral finding data. Nothing on the Audacity side relies on REAPER ExtState or take-marker semantics. Take management has no direct Audacity equivalent.
- **Proof gates a note's DAW actions by capability** (DQ-18 in the [Studio Next Proof and Pickups PRD](../prds/studio-next-proof-and-pickups.prd.md#decisions), superseding). The Inspector's Show in and Add marker in the DAW (`apps/ui/src/components/proof/inspector/InspectorActions.tsx`) read `navigate` and `markers` from the DAW port's `capabilities()` and show the capability's own sentence when one is off; the labels take the DAW's name from the same report, and no branch depends on which DAW it is. Trim the gap (`inspector/TrimGap.tsx`) reads `cut_range` and calls Editing's gap operation. Proof has no take review or take comparison since SN-Q9. `apps/ui/src/useDawKind.ts` still reads the session's `daw` for wording, such as the Pickups session panel's marker button.
- **`--daw Audacity`**. The app accepts it the way the REAPER launcher passes `--daw REAPER`; `dawport.Classify` is the only reader of the label (case-insensitive; anything but REAPER or Audacity selects nothing). An Audacity launch opens no REAPER file bridge even if a `--session-dir` is passed, its review workflow refuses every request with "Audacity support is not available yet. …" except for the pipe client's capabilities above, and it resolves the three settings tiers below with no Audacity-specific code (proved by `apps/desktop/audacity_test.go` and `libs/python/tests/test_config_audacity.py` on an `.aup3` project with no `.rpp`).

## The built-in recorder as an engine

- **A DAW kind of its own, `Built-in`** (`dawport.KindBuiltIn`). A launch with no DAW whose project records with the built-in recorder (the `Recording.engine` row, written only by `RecorderChooseEngine`) has it as its engine; so does `--daw Built-in`. A REAPER or Audacity launch keeps its DAW whatever the project chose. `dawLaunchKind` (`apps/desktop/bindings_daw.go`) is the host's one reader, through `dawport.LaunchKind`.
- **The adapter wraps the recorder, it does not change it.** `apps/desktop/internal/dawport/builtin` declares a small `Recorder` interface that `recording.Service` satisfies, and maps `record` and `takes` onto it (Experimental). It keeps no saved project, so `project_read` is Unsupported with its own sentence; punch and the edits the app will make itself are Not yet available; the rest is Unsupported. It reports its own runtime, always there and answering, since there is no bridge to connect. What it declares, and the source of each row, is [the built-in recorder reference](../reference/daw/builtin-recorder.md).

## The DAW port

Every DAW action reaches an engine through `apps/desktop/internal/dawport` (for the review workflow, the event vocabulary is part of the contract). An adapter per engine — `dawport/reaper` today, `dawport/audacity` as a declaration only until its pipe client exists — declares a `port.Level` for each capability and implements one small role interface for every capability it has (`ReviewSession` is the review workflow's role). A `dawport.Resolver` alone decides what is usable right now, from that declaration, runtime reachability and the narrator's per-capability `DAW.capability.<name>` toggle.

The capabilities, each role interface, what a conforming engine returns and the level each engine declares are in the [DAW reference](../reference/daw/README.md): [capabilities](../reference/daw/capabilities.md) for the catalog and [the matrix](../reference/daw/matrix.md), which is generated from the adapters' declarations. The mastering port's render rows (`render_with_fx`, `master_chain_read`, `macro_render`) are Experimental or Unsupported by design ([Provider ports](provider-ports.md), [The REAPER bridge and its test harness](reaper-bridge.md), [`macro_render`](../reference/daw/capabilities.md#macro_render)).

- **Requests in, events out**: an asynchronous role's method only hands a request to the engine and returns an error when it could not be sent; the answer arrives later as an event tagged with the run ID. `dawport.Event` and `Subscription` alias the bridge's own types, so the event tags and fields in `internal/bridge/wire.go` stay part of the contract: a second adapter reports the same events rather than the service growing a second parser.
- **Callers take a role, not the bridge client.** A package asks a `dawport.Resolver` for a role through `dawport.Role[T]` instead of holding `*bridge.Client` or `*bridge.Actions`; `internal/dawport/boundary_test.go` fails on a holder outside `internal/bridge` and `dawport/reaper` that is not in its named exceptions list (`app.go`, `services.go`, `bindings_navigation.go`, `internal/daw/reachability.go`). It likewise fails on code outside `dawport` that branches on a DAW's kind or label, apart from the exceptions it names (`app.go`'s `configureLocked`, `pickerSwitchDAW` in `apps/desktop/bindings.go`, `dawDeclarationFor` in `bindings_daw.go`). Everything else asks the resolver for a capability.
- **Per-capability toggles replace the one switch.** `DAW.capability.<name>` (`auto | on | off`, append-only in `config/defaults.json`) lets the narrator turn on one capability without the rest: `auto` means on when Supported, and on when Experimental only while the old `DAW.experimental_reaper_actions` switch (still read) is also on. Promoting a verified REAPER command from Experimental to Supported (after the owner's REAPER verification pass) is then a one-line change to `dawport/reaper`'s declaration, not a new caller change.
- **A capability can require another.** The resolver checks the declaration, then the settings, then the runtime. An adapter that is a `dawport.Requirer` names, per capability, the capabilities it needs (beside the catalogue's `Spec.Requires`, empty today), and the resolver checks each requirement's declaration and settings after the capability's own and its runtime after the capability's runtime. A capability whose requirement is unavailable is refused with that requirement's reason, worded by the adapter (`dawport.RequirementExplainer`) or as "<label> needs <label>." followed by the requirement's sentence. A capability the adapter declares destructive is not refused for its requirement; the resolver reports it not destructive while every requirement is available. `Declares()` stays static. Audacity uses this for the five capabilities it has only with `backups` ([Audacity 3](../reference/daw/audacity-3.md#what-needs-backups)), and the conformance suite (`dawporttest`) fails a requirement that names no capability or closes a cycle.
- **The UI reads one binding and one event.** `Host.DawCapabilities()` and `daw_capabilities_changed` carry `{daw, reachable, capabilities: {<name>: {level, available, reason?, message?, destructive?, mode?}}}` (`apps/ui/src/api/schemas/daw.ts`); a control never words its own refusal, reading `CapabilityGate`/`useCapability` instead ([design-system.md](../design/design-system.md#primitive-components)). `destructive` (sent only when true) and `mode` (`native`, `app` or `steps`) are what an adapter declares through `dawport.Describer`, reported whether or not the capability is available now. REAPER and Audacity declare them.
- **A DAW call answers a `dawport.Result`** (`internal/dawport/result.go`): `{ok, changed, message, undoSteps, refused?, code?, steps?}`, with `undoSteps` from 0 to 12. `OK` counts one undo step for a change, `Refused` changes nothing and repeats its reason as `message`, and `RefusedFrom` turns a capability refusal into a `Result` carrying the refusal's own sentence. `RefusedStale` adds `code: "stale"`, the only code, for an id the DAW no longer has where the app read it; the page branches on the code and shows the sentence. Until the bindings return a `Result`, the UI `DawClient` (`apps/ui/src/ports/daw.ts`) sets the code from a host `reason` of `stale`, or `track_missing` for a record start. Its goldens are `tests/fixtures/contracts/daw-result-*.json`. The edit roles return it: `RangeCutter` (`cut_range`), `RangeFXApplier` (`fx_range`), `TakeStacker` (`stack_takes`) and `BackupKeeper` (`backups`), whose requests are `dawport`'s own types (`DeleteRangeRequest`, `FXRangeRequest`, `StackRequest`, `BackupRequest`) naming items, takes and times, never a path. REAPER declares the first three Experimental and `backups` not yet available; Audacity declares all four Experimental, and its roles for the first three refuse until their steps are built.
- **The capabilities added after the edit roles** (the full catalogue and levels are in [the matrix](../reference/daw/matrix.md), generated from the declarations): `file_preview` (`FilePreviewer`) and `file_reveal` (`FileRevealer`) act on rendered files that are not project items and leave the project unchanged; `range_gain` (`RangeGainReducer`) and `click_repair` (`ClickRepairer`) are the edits behind Clean up; `undo_last` (`LastActionUndoer`) reads whether the engine's next undo point is one an app action made and undoes it, so the app's Undo of a cut reaches the DAW (the journal's rule is in [UI state and the command journal](ui-state-and-journal.md)); `monitor_level` (`MonitorLeveler`) reads and sets the level the narrator hears, a 0 to 100 whole number the engine maps to its own monitoring output; `input_level` (`InputLeveler`) is declared Unsupported by every engine that can be reached (REAPER, Audacity 3, the built-in recorder) because no engine can set an interface's input gain, so the narrator is sent to the interface's control panel. REAPER declares the first six Experimental. Audacity 3 declares `range_gain` and `click_repair` Experimental and, like the other edit roles, refuses them with the backups sentence while Audio backups is off (`audacity/steps.go`), and leaves `file_preview`, `file_reveal`, `undo_last` and `monitor_level` not yet available. The built-in recorder declares `undo_last` not yet available.
- **Pickup markers are the DAW's truth.** A pickup is open while its marker is named `PICKUP:` and done once it is `PICKUP_DONE:`. The UI `DawClient`'s `addPickupMarkers`, `setPickupMarkerDone` and `readPickupMarkers` run over the `PickupsImport`, `PickupsResolve`, `PickupsReopen` and `PickupsListMarkers` bindings and wait for the run's `pickups:state`. The DAW addresses a marker by its time, so each client keeps the time of every pickup id it marked or read in its session; an id it does not know answers "Nothing to change." with `changed: false`. A DAW that does not answer is refused with the `pickups` capability's own sentence, and the client queues nothing: a page that wants a write to wait keeps its own queue.
- **The REAPER review session** (`dawport/reaper`'s unexported `review` type, `review.go`) puts exactly the bridge command a request needs: `prepare_compare`, `inspect_compare_results`, `jump_to_compare_marker`, `export_compare_markers`, answered by `COMPARE_PREPARED`, `COMPARE_MARKER` per finding then `COMPARE_INSPECTED`, no event, and `COMPARE_EXPORT_MARKER` per finding then `COMPARE_EXPORTED` respectively — the same as the `dawadapter.Reaper` it replaced. On an Audacity launch, `dawport/audacity.UnavailableReview()` refuses every request with the [Audacity boundary](#audacity-boundary) sentence instead.
- **Construction.** In `configureLocked`, the host picks the review session by the launch's `--daw`: `reaper.ReviewFor(client)` (nil for a standalone launch, since there is no bridge to wrap) unless the launch is Audacity, which gets `audacity.UnavailableReview()` regardless. `transcript.NewWithReview` builds the service over whichever session that is; `internal/transcript/adapter_test.go` runs the whole review loop against a fake `dawport.ReviewSession`.
- **Take management** (take creation, pickups, line identity, render setup) has no Audacity equivalent (see "Audacity boundary" above); rather than being absent from the port, those roles are simply `NotYetAvailable` on the Audacity adapter, like every other capability it does not implement yet.
- **Not yet in the interface.** Marking a finding reviewed and exporting the reviewed set have no DAW command ([#1477](https://github.com/countrymanprime/narration-utils/issues/1477)).

## The DAW catalog and "Get it" flow

Upstream of everything else on this page: a first-time narrator has no DAW installed yet, and nothing above helps
until one exists on the machine. `apps/desktop/internal/dawcatalog` (Go) answers, on demand, whether a supported
DAW appears to be installed, and Settings' global-scope **DAW Integration** category shows that fact with a way to
get the DAW and a way to re-check after installing it. The app never downloads, verifies, bundles, or executes a
DAW installer — it only opens the vendor's own download page in the narrator's default browser and reads
registry/filesystem state.

**Catalog.** `dawcatalog.Catalog` is a Go literal — today just `dawcatalog.REAPER` (name, publisher, one neutral
licensing line, and `reaper.fm`'s own download-page URL) — never loaded from a file or fetched at runtime, so the
destination of every "Get it" click is auditable in code review. Audacity has no entry yet: it is deferred until
`docs/roadmap.md`'s own precondition (a proven shared contract and REAPER workflow) is met, to avoid advertising a
capability with no working adapter behind it.

**Detection.** `dawcatalog.Detect`/`DetectAll` run on demand, never polled, behind a fakeable `Detector` interface.
The Windows lookup is `apps/desktop/internal/daw.LocateReaperExecutable` — the same registry-then-file-association
locator the launcher uses, verified against a real REAPER install (`apps/desktop/internal/daw/locate.go`) — so
this package answers "is a supported DAW here" with the identical fact the launcher already resolves,
instead of a second, possibly-drifting lookup. A portable REAPER install that never registers itself is a soft
false negative: the narrator can still use "Get REAPER" or their own copy, and nothing here blocks any feature on
detection (see below).

**The UI.** `Host.DawCatalogList()` returns the catalog plus each entry's live detection state; `Host.DawCatalogOpenDownloadPage(id)` looks the id up server-side in `dawcatalog.Catalog` and opens it with `openInBrowser` (`apps/desktop/wailsapp.go`) — the id, not a URL, crosses the Wails boundary, so nothing UI-supplied can pick an arbitrary destination (the same trusted-URL discipline `update.go`'s `openReleaseNotes` already uses for release notes). `DawCatalogPanel` (`apps/ui/src/components/settings/DawCatalogPanel.tsx`), shown in Settings' global-scope DAW Integration category:

- Lists each entry with a detected/not-detected dot and its publisher/licence line.
- Offers a **"Get `<name>`"** button on an undetected entry, which opens the vendor's download page; the button
  disables and reads "Opening…" while the browser call is in flight, so a narrator cannot open two tabs.
- Offers a **"Check again"** button that re-runs the same detection call the panel's mount already makes (one call
  site, two triggers — the same pattern `LocalAssets`' mount-plus-"Try again" uses), reading "Checking…" and
  disabled meanwhile, so a narrator who just installed a DAW sees it detected without leaving Settings.
- Offers a **"Link a REAPER project file"** handoff button on a detected-but-not-yet-linked entry, which calls the
  one shared `linkDawFile()` action Settings' project-scoped DAW panel, and the audio engine panel
  already use — no separate binding, no new file dialog. It is
  hidden once a project is already linked, since it would have nothing left to offer.

**What detection does not do.** It never gates a feature: Tracks and Proofing are still gated on a *linked* project
file (see above), not on whether a DAW was *detected*. This keeps the two facts — "is a DAW on this machine" and
"is a DAW file linked to this project" — from becoming a second, redundant gate a narrator has to satisfy twice.

**Trust boundary.** Registry/filesystem inspection to detect third-party software and opening a browser to a
hardcoded, compile-time URL are both covered in [the threat model](threat-model.md); the URL's spoofing risk is nil
because it is a Go constant, never derived from anything the narrator or network supplies.
