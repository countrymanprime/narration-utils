# 0405. Pronunciation stays local-first behind CMU, Wiktextract and eSpeak, with Merriam-Webster as the one narrator-keyed online source

**Status:** Proposed
**Date:** 2026-09-27
**Supersedes:** for pronunciation dictionary data only — narrows [`prep-depth.prd.md`](../prds/prep-depth.prd.md)'s Success Metrics row "No network call from the app for a lookup" and [`provider-ports.md`](../architecture/provider-ports.md) Open Question Q5's "never fetched by the app" wording for the `PronunciationSource` port. Neither of those is itself an ADR, so nothing here is superseded in the ADR sense (Rule 2 of [`docs/adr/README.md`](README.md)); this ADR is the decision record those two documents' own text will be updated to match, in the phase that implements it (Phase 9 of `prep-depth.prd.md`), not in this pull request.

## Context

The owner's decision D72 (recorded on issues #509/#510) deepens prep-depth's pronunciation feature two ways the PRD as written did not anticipate:

1. **An offline precedence chain**, not just a single dictionary with a fallback: the narrator's own entry, then the CMU Pronouncing Dictionary, then Wiktionary's IPA data (through the Wiktextract project's structured extracts, published at kaikki.org), then a clearly labelled letter-to-sound guess for anything no dictionary has. The owner-approved prep-script mock's "Say it" column shows a source per row, which is the UI contract this chain answers into.
2. **One optional online source**, the Merriam-Webster Dictionary API, on the narrator's own free API key (never a key this project supplies or shares), reached with a prompt that opens `dictionaryapi.com`'s sign-up page in the browser and takes the pasted key.
3. **Wikimedia Commons audio links** surfaced from the same Wiktextract data, played or opened on request.

This matters because two documents already say something absolute that the second point contradicts. `prep-depth.prd.md`'s own Success Metrics: "No network call from the app for a lookup ... `BrowserLookup` opens a URL through the host's existing 'open externally' path and makes zero HTTP requests itself." `provider-ports.md` Open Question Q5: a `BrowserLookup` role "returns a URL the host opens, never fetched by the app." Both statements were true of every pronunciation source this app has shipped so far (`cmu`, `espeak`, and the four Phase 2 browser lookups including Merriam-Webster's own browser page). D72 asks for a second, narrower thing behind the same port: a role that *does* fetch, from exactly one host, only on the narrator's own account, only a single word at a time.

Three licences need a decision, not just a lookup, because this project already has a five-class licence policy ([`local-dependency-evaluation.md`](../research/local-dependency-evaluation.md#license-classes)) that a new dependency is checked against before it ships:

- **CMU dictionary** (`cmudict`/`pronouncing`) is already an accepted dependency (`local-dependency-evaluation.md:214`); no new decision.
- **eSpeak NG** (via `phonemizer`, GPL-3.0-or-later data and code) is already shipped in the frozen Story Bible sidecar and already accepted under the existing policy's "Strong copyleft" class: "Narration Utils is itself AGPL-3.0-or-later ... and already ships GPL-family code in the frozen Story Bible sidecar (Piper, phonemizer, eSpeak NG data), so a GPL-3.0-or-later component is compatible." D72's own prompt raised evaluating it "like the FFmpeg build" or finding a permissive alternative; neither is needed, because this dependency was accepted once already and nothing about shipping it as a *labelled* letter-to-sound guess (rather than an unlabelled fallback) changes its licence terms.
- **Wiktionary / Wiktextract is the one new licence.** The same research doc already considered it once, for the reader's offline dictionary lookup, and explicitly deferred it: "Wiktionary-derived extracts | Share-alike terms (CC BY-SA), not one of the four classes in License classes | ... | Deferred: share-alike is not yet a reviewed class in this policy; would need its own policy decision before adoption, not folded into this one." This ADR is that policy decision, scoped narrowly to this feature's displayed IPA data.
- **Wikimedia Commons audio** carries a per-file licence (Commons requires every upload to declare one, typically a CC variant or public domain), which this app never needs to clear because it never redistributes the file — it only opens or hands off the link (Decision, below).

No credential store exists in this app today (`apps/desktop/internal/settings/store.go` keeps every setting in plain per-user/per-project JSON; nothing in the repository imports a platform keyring). Merriam-Webster's API key is the first secret this app stores at rest, so where it goes and how it is protected needs a decision too, not just an implementation.

**Not verified in this session.** The egress proxy refused `kaikki.org`, `en.wiktionary.org` and `dictionaryapi.com` (checked 2026-09-27, `EGRESS_BLOCKED`). The licence terms and dataset shape below are stated per each project's own public documentation, not re-read live in this session — the same "per upstream docs, not verified here" posture [`ffmpeg-encoder-build.md`](../research/ffmpeg-encoder-build.md) already used for sources its own session could not reach. Wiktextract's exact release file, size and hash, and Merriam-Webster's exact sign-up flow and rate-limit terms, are re-verified by the implementing phases' own Phase 0 steps (`prep-depth.prd.md` Phases 8 and 9) once a session can reach either host.

## Decision

**Pronunciation stays local-first.** The `PronunciationSource` port (`libs/python/narration_common/ports/pronunciation.py`, `provider-ports.md`) keeps its `pronounce` (offline) and `browse` (browser-opened, never fetched) roles exactly as they are for every source that has them today. Nothing about Phase 2's four browser lookups (Forvo, YouGlish, Merriam-Webster's own site, Howjsay) changes.

1. **Offline precedence chain.** The build-time fallback tries registered sources in registration order (`SourceRegistry.fallback_order()`, unchanged code): `cmu` → a new `wiktextract` row → `espeak`. This is additive registration, not a new mechanism. The narrator's own entry (`GuidePronunciation.chosen`/`alternate`, prep-depth Phase 1, #745) sits outside this registry entirely and always wins when present, exactly as it already does. `wiktextract` is a new `PronunciationSource` row (`pronounce` mode only, like `cmu` and `espeak`), backed by a Wiktextract-derived offline lookup index, catalogued and downloaded through the existing asset-manager pattern (`internal/assets`, the same shape as the Open English WordNet dictionary and the FFmpeg encoder build catalog rows): a pinned, immutable, hashed URL; a narrator-confirmed first-use download; only a small derived index kept at install, never the raw multi-gigabyte Wiktextract dump ([ADR 0136](0136-an-asset-may-keep-only-a-file-built-at-install-from-its-verified-archive.md)'s Derive step). Every displayed Wiktextract answer carries CC BY-SA attribution to Wiktionary and its contributors, in the UI (the same per-answer attribution the reader's WordNet lookup already shows, [ADR 0097](0097-the-manuscript-reader-word-lookup-uses-the-open-english-wordnet-as-a-downloadable-asset.md)) and in `THIRD-PARTY-NOTICES.txt`. The existing `EspeakSource` answer is relabelled to read clearly as a letter-to-sound guess (not a dictionary hit), with no change to eSpeak NG's own licence terms or how it is shipped.

2. **Merriam-Webster is the one online `PronunciationSource` role that fetches.** A new role (distinct from `browse`, which never fetches) is added to the port, declared only by a Merriam-Webster adapter, for exactly this one host. The role's contract:
   - The narrator supplies their **own** Merriam-Webster Dictionary API key. This project never bundles, generates or shares a key; one shared project key would exceed the free tier's per-key limits and likely breach Merriam-Webster's own terms, so no such key exists anywhere in this project's code, catalog or defaults.
   - **First use** opens `dictionaryapi.com`'s free sign-up page in the narrator's default browser (the same "open externally" host call every browser lookup and every other outbound URL in this app already uses) and takes the pasted key through a Settings field built for this purpose.
   - **Key storage:** on Windows, the key is encrypted at rest with `CryptProtectData` (DPAPI, current-user scope) and stored as an opaque blob in the per-user settings file; it is decrypted only in memory for the length of one lookup request. On macOS and Linux (preview builds with no installer yet, per [first-use provisioning](../architecture/first-use-dependency-provisioning.md)'s "Windows first" section), the key is stored in the same per-user file in the clear, with a Settings-page note that the platform credential store is not implemented there yet. No new third-party keyring dependency is added: a Windows syscall wrapper is already reachable from the existing toolchain, and a cross-platform keyring library would add exactly the kind of new trust surface `provider-ports.md` already declines to add for Python plugins ("plugins would widen the trust boundary").
   - **The key, and any word looked up, is never logged.** It never appears in the host log (`hostlog`'s existing "never the data" policy extends to this key) or the run log, and never in a diagnostics export.
   - **Privacy rule (D72), enforced as a contract, not a convention:**
     - An online lookup sends a **single word only** — never a passage, a file name or a project id. The request is built by the host from the looked-up word alone; the UI never supplies a URL, query string or extra field the request could carry.
     - A lookup is **narrator-initiated** (one click, no confirmation dialog, matching Phase 2's existing browser lookups) **or opt-in with a notice for a batch** (looking up every un-confirmed pronunciation query at once needs one confirmation naming the word count before it starts).
     - **Results are cached locally**, beside the existing pronunciation entry, so a repeat lookup of the same word makes no second request and an offline narrator still sees the last answer.
     - **No telemetry, and no project-run proxy.** The request goes straight from the narrator's own machine to Merriam-Webster's API on the narrator's own key; nothing about this feature introduces a server of this project's own, and nothing here changes the "no telemetry, no analytics, no account" statement the threat model already makes about everything else this app does.
   - This is a genuinely new outbound-trust boundary: the Go host's `depguard` rule (`.golangci.yml`), which today allows `net`/`crypto/tls`/`golang.org/x/net` imports in exactly three places (`internal/assets`, `internal/update`, root `media.go`), gains one more narrowly scoped allow row for this feature's own package. The threat-model row and the `SECURITY.md` bullet this boundary needs are scope items of the phase that implements it (`prep-depth.prd.md` Phase 9), not of this ADR or the PRD update it accompanies.

3. **Wikimedia Commons audio links are opened or handed to the OS, never fetched by the app.** Surfaced from the same Wiktextract-derived data (a Commons audio filename or URL per word, where Wiktextract records one), the app opens the link through the existing "open externally" host call, exactly like a `BrowserLookup` role, and never constructs an HTTP client to stream or cache the audio itself. Because the app never redistributes the file, the per-file licence Commons assigns to that particular recording (which varies file to file) is the narrator's own listening choice, not a distribution decision this project has to clear in advance.

## Consequences

- **Easier:** a narrator gets a materially better offline dictionary (Wiktextract covers far more headwords and variant pronunciations than CMU alone) before ever touching the network, and a genuine online fallback for the words no offline source can answer, without weakening the "no network call" guarantee for the four existing browser lookups or for `espeak`/`cmu`.
- **Easier:** the licence question this project deferred once (Wiktionary/Wiktextract's CC BY-SA terms) now has an explicit, narrow answer instead of blocking every future use of Wiktionary-derived data; a later feature that wants to reuse Wiktextract data for something other than displayed, attributed IPA strings needs its own ADR, because this one's scope is pronunciation display only.
- **Harder:** the Go host's `depguard` allow-list, previously exactly three rows, now has a fourth, and every future security review of "what can this app send off the machine" has one more row to check (accepted: the row is narrow, one host, one word, narrator-keyed).
- **Harder:** this app now stores one secret at rest for the first time; a bug in the Q10 storage path (ADR context) is now possible in a way it was not before Phase 9 ships. The DPAPI scope (Windows) bounds the residual risk to "another process of the same Windows user," the same residual risk this app's threat model already accepts for the REAPER bridge and the extracted sidecars, so this does not introduce a new class of risk, only a new instance of the existing one.
- **What a future change would need to do to override this:** a decision to fetch anything beyond a single word for Merriam-Webster, to add a second online `PronunciationSource`, to change where the key is stored, or to relax the "opened, never fetched" rule for Commons audio, each needs its own ADR that supersedes this one (Rule 1/2 of [`docs/adr/README.md`](README.md)) — this ADR's scope is exactly the three points in Decision, nothing wider.
