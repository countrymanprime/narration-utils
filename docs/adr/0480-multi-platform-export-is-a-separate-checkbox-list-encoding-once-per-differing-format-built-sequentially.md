# 0480. Multi-platform export is a separate checkbox list, encoding once per differing format, built sequentially

**Status:** Proposed (point 1, the separate checkbox list, is superseded by [ADR 0745](0745-master-and-qcs-outputs-list-names-the-files-the-acx-package-will-create-and-the-multi-platform-card-is-gone.md): the card is gone from the page)
**Date:** 2026-09-28

## Context

[render-encode-master](../prds/render-encode-master.prd.md) Phase 6 asks for "one mastered/encoded source produces packages for several selected profiles in one action," on top of Phase 5's export/package split (`apps/desktop/export_job.go`, `apps/desktop/package_job.go`) and [ADR 0440](0440-master-and-qcs-platform-tabs-are-the-projects-delivery-profile-and-the-page-draws-only-what-the-host-measures.md), which made Master & QC's platform tabs the project's own single choice of delivery profile (`deliverySelectProfile('project', …)`). Building the new feature raised four questions with no PRD-level answer:

1. Do the existing platform tabs become the multi-select, or does a new control own it? Repurposing the tabs would collide with ADR 0440's own decision: the tabs are what the *page itself is judged against*, read by `MasterQcPage.tsx`'s single-file and book panels. A multi-select there would silently break that meaning for anyone reading ADR 0440 later.
2. `internal/deliveryprofile.Profile` has no field naming a profile's required container format; the only signal is a `Rule` whose `Metric` happens to end in `_format` (today only ACX's `mp3_format`). Something has to read that convention to know when a re-encode is needed, and it needs a home.
3. Building several profiles' packages could run concurrently (separate subprocess encodes, separate output folders) or one at a time. Each has a real cost.
4. Two selected profiles can share a required format that differs from the export job's own current one; encoding for that format must not happen twice.

## Decision

1. **The platform tabs stay a single-select choice of the project's own judged profile** (ADR 0440, unchanged). Multi-platform export is a **separate checkbox list**, one row per profile the host lists (the same `profiles.profiles` the tabs already read), in a new panel `MultiPlatformExportPanel.tsx` beside `DeliveryPackagePanel.tsx` in `MasterQcPage.tsx`'s right-hand column. Checking a box never changes which profile the page's own checks are judged against; it only marks a platform to build a package for.
2. **A generic `_format`-suffix convention lives in `apps/desktop`, not `internal/deliveryprofile` or `internal/packager`.** `requiredFormat(profile)` (`apps/desktop/multi_package_job.go`) reads a profile's rules for the first file-scope rule whose `Metric` matches `^(\w+)_format$` and returns that capture group, defaulting to `"mp3"` when none exists. It is a caller's own reading of an existing naming convention those two packages already use (ACX's `mp3_format`), not a new field on a type several tools share; adding a `Format` field to `Profile` would mean every consumer of `internal/deliveryprofile` (the measurement judge, the packager's checklist, the profile editor) has to agree on what it means for a rule to also be "the" format, when today it is simply one file-scope rule like any other.
3. **Packages are built sequentially, one profile at a time, not concurrently.** They can share filesystem paths (subfolders of one narrator-chosen root) and the encoder's own subprocess use (`internal/encodeport`); running them at once would mean coordinating two writers into related paths and two encoder invocations competing for the same resource, for a feature whose success metric ("a distinct, correctly-named package for each profile … with no re-encode unless the format differs") says nothing about wall-clock time. Sequential order also makes Cancel simple: it stops before the next profile starts, and a profile not yet reached is left `"pending"` (`MultiPackageResult.Phase` has no per-profile `"cancelled"` - the whole job's own `Phase` already reports that a cancel happened).
4. **Re-encoding is memoized by format, not by selection.** `startMultiPackage` groups selections by `requiredFormat`; the format matching the export job's own current format reuses its already-encoded files (`ExportFileResult.EncodedPath`) unchanged, and every other format is encoded exactly once, into `exportScratchDir(projectFolder, "encoded-"+format)`, and reused by every selection that needs that same format. This is what makes the PRD's own two test requirements true: "two profiles sharing MP3 at the same bitrate reuse one encoded file" (they share the export job's current format, so nothing is re-encoded at all) and "a profile requiring M4B triggers a second encode only for that format" (one encode per export-job file, however many selected profiles need M4B).

## Consequences

- A narrator who wants a package for a platform never has to change what the page's own checks are judged against, and vice versa: the two controls stay legible as different questions ("what am I checking against" vs. "what am I packaging for").
- A future profile with its own real format field (rather than the `_format`-suffix convention) would need a new ADR superseding point 2 here, and a decision about whether `requiredFormat` moves into `internal/deliveryprofile` at that point.
- Building N profiles' packages takes roughly N times as long as building one when their formats all differ, since nothing runs concurrently; this was accepted as the simpler, safer default until a narrator's own use shows it matters.
- Cancelling a multi-platform build mid-run never leaves two packages half-written at once, because only one profile is ever being assembled at a time.
