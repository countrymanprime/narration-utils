# 0340. A P5 async role is taken from the live adapter, not `Resolver.Role`, and only the toggle gates the send

**Status:** Proposed
**Date:** 2026-09-27
**Supersedes:** none. It fills in a gap [ADR 0302](0302-dawport-roles-exchange-the-bridges-own-types-through-aliases-and-an-asynchronous-role-is-one-method-per-command.md) left open for the [DAW port PRD](../prds/daw-port-and-capabilities.prd.md)'s Phase 5 migrations, worked out while building Phase 5c (`internal/retakelanes`, `internal/projectstate`, `internal/takereview`, and `internal/daw`'s reachability behind `Heartbeat`).

## Context

Every async capability P5c touches (`retake_lanes`, `project_state`, `take_create`) is declared `NeedsRunning` in the capability catalog (`internal/dawport/capability.go`). `Resolver.Support(c)` - and therefore `dawport.Role[T]` - refuses a `NeedsRunning` capability outright while `Runtime.Reachable` is false, i.e. before REAPER's heartbeat is fresh.

`configureLocked` builds each of `retakelanes.Service`, `projectstate.Service` and the take-review binding once per project switch, at the moment the bridge client is opened and before any heartbeat has arrived. If the role were fetched with `dawport.Role[T]` at that moment, every migrated service would start permanently unavailable, since nothing re-fetches the role later: [ADR 0302](0302-dawport-roles-exchange-the-bridges-own-types-through-aliases-and-an-asynchronous-role-is-one-method-per-command.md) says "The P5 migrations are meant to change constructors only", so re-deriving the role on every `Pick`/`Check`/`CreateTake` call was not the intended shape either - it would also gate `Subscribe`/`Dispatch` behind reachability, which every existing bridge consumer (`Navigator`, `Actions`, `Reachability` itself) subscribes and dispatches unconditionally, reachable or not.

`Resolver.Allowed(c)`, added in [ADR 0304](0304-bridge-actions-asks-a-per-command-gate-and-the-daw-ports-resolver-answers-it-from-the-per-capability-settings.md) for `bridge.Actions`, already solves the equivalent problem there: it checks only the declaration and the narrator's per-capability toggle, never the runtime, "so a permitted command still behaves as before when REAPER is closed" - the send goes out and fails on its own terms, as it always did.

## Decision

- A P5 async role (`RetakeLanePicker`, `ProjectStateReader`, `TakeCreator`, and any future `NeedsRunning` async role a later P5 phase migrates) is taken directly from a live adapter's `Role(c)`, once, at the same point in `configureLocked` the old `*bridge.Client` was handed to the service's constructor. It is not filtered through `Resolver.Support` / `dawport.Role[T]`, which would additionally (and wrongly, for this case) refuse it while REAPER's heartbeat has not yet arrived or has gone stale.
- The send method the role exposes (`PickRetakeLane`, `RequestProjectState`, `CreateTake`) is still gated by `Resolver.Allowed(c)`, the same declaration-and-toggle check `bridge.Actions` already asks (ADR 0304): `configureLocked` passes the same `Resolver.Allowed` it builds for `h.actions` into `reaper.New` as the live adapter's `allowed` parameter, so a narrator's `DAW.capability.<name> = off` refuses these three commands too, with no behaviour change on default settings (`auto` is permitted for every `Supported` capability).
- `Subscribe`/`Dispatch` are never gated at all, matching every other bridge consumer: they only register a callback or read `events.log`, neither of which needs the engine to be answering right now.
- Read-only roles the resolver's `Support` legitimately should gate (the `DawCapabilities` payload, `daw_transport_changed`) are unaffected: they still go through `Resolver.Support`/`Role[T]`, since telling the narrator "REAPER is not answering" is exactly `Support`'s job for a payload, not a live command.
- Each P5 phase builds its own live adapter over the shared bridge client for the roles it needs (`internal/dawport/reaper.New(client, resolver.Allowed)`), rather than sharing one: `bindings_daw.go`'s P4 comment already anticipated this ("P5a's registry adapters give every consumer... the same resolver; until then each caller builds its own"). This duplicates the adapter's internal `bridge.Actions`, `bridge.Navigator` and `daw.Reachability` per phase (each an independent, harmless consumer of the same client's fan-out, ADR 0068), until P5a's shared registry adapter replaces every phase's own copy with one.
- `internal/daw`'s reachability keeps its existing construction (`daw.NewReachability(client)`, unconditionally valid even for a nil client) but every holder outside `internal/daw` now types it as `dawport.Heartbeat`, not `*daw.Reachability`, so a consumer depends on the role, never the REAPER-only concrete type. A test that must synthesize a heartbeat still needs the concrete type (`Record` is not part of `Heartbeat`), so it keeps a `*daw.Reachability` handle alongside the `Host` it configures.

## Consequences

- A P5 async role migration changes exactly what ADR 0302 promised: the constructor's parameter type, and the `Send("<command>", …)` lines it replaces. No caller becomes reachability-sensitive in a way it was not before.
- The narrator's `DAW.capability.retake_lanes` / `.project_state` / `.take_create` toggles (added, unused, in Phase 3) take effect for the first time in Phase 5c, at no behaviour change on default settings.
- Harder: until P5a's shared registry adapter lands, each of P5a-P5d builds its own live REAPER adapter for the roles it needs, so there are as many redundant `daw.Reachability`/`bridge.Actions` instances on one client as migrated phases. None of them subscribe to anything the others do not already also fan out correctly (ADR 0068), so this costs memory, not correctness.
- Overriding this - gating an async role's send on the full `Support` (including reachability) after all - needs a new ADR, since it would refuse a send while REAPER is merely slow to heartbeat rather than actually gone, a behaviour change these services do not have today.
