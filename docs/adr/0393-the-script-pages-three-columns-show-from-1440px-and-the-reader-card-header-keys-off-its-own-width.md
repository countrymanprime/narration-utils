# 0393. The Script page's three columns show from 1440 px, and the reader card's header keys off its own width

**Status:** Accepted
**Date:** 2026-09-28
**Supersedes:** ADR-0392 (point 2, the rail's breakpoint, only - its other two decisions stand)

## Context

[ADR 0392](0392-the-script-pages-prep-status-is-the-names-still-to-confirm-and-its-rail-is-a-panel-below-2xl.md) put the Script page's rail (mock 02's Pronunciations/Characters/Queries column) behind Tailwind's `2xl` (1536 px), not the mock's own 1440 px capture width: at 1440 px, beside the navigation's labelled rail, three columns left the reader about 680 px, and the reader card's header - a viewport breakpoint (`md`, 768 px) deciding whether its right-side cluster (an optional Retail sample tag, the word-count/read-time stat block, the action slot, the chevron) sits beside the title or wraps below it - assumed a viewport that wide always meant a card that wide too. That assumption broke: the card's own rendered width at three columns (as little as ~520-630 px) is narrower than plenty of viewports where the reader is still full width, so the cluster overflowed or clipped instead of wrapping (found by the visual suite's `retail-sample` and `markup-dialog` states).

The owner settled this on issue #509, **D85** (2026-09-28), answering the visual-mockup-divergence audit's Q3: **"Three columns as drawn [at 1440 px]. Below that, the rail becomes a slide-over."** This is binding, not a recommendation - "the approved mocks win."

## Decision

1. **The rail column shows from 1440 px, not `2xl` (1536 px).** The outer grid's rail breakpoint (`apps/ui/src/components/script/ScriptPage.tsx`) and the "Prep rail" band button's breakpoint both move to an arbitrary `min-[1440px]` variant, matching mock 02's own capture width exactly (D85's mandatory number - the mock's own screenshot, not a nearby round Tailwind step). Below it, the rail is still the existing slide-over panel; nothing about that panel changes, only the width that reaches it. The two-column breakpoint (the chapter list, from 1280 px) moves from Tailwind's named `xl` to the arbitrary `min-[1280px]`, for the reason in point 2.
2. **The reader card's header keys its cluster-wrap decision off the card's own rendered width, not the viewport.** `apps/ui/src/components/manuscript/ReaderCard.tsx`'s card becomes a CSS container (`@container`, `container-type: inline-size` - built into Tailwind v4, confirmed against the installed `tailwindcss@4.3.3`), and the header's `md:`/`max-md:` viewport variants become `@min-[40rem]:`/`@max-[40rem]:` container variants on that same property. 40 rem (640 px) is the card width the fixed-width cluster (the optional tag, the 6.5rem stat block, the 13rem action slot, their gaps, the chevron) needs to sit beside a legible title; below it, the header stacks exactly as it already did below `md`. This makes the header correct in every context it renders in - Script's two- and three-column modes, a narrower Booth/companion panel - rather than assuming a viewport width implies a card width. Verified empirically (real 1440 px renders, not just the compiled CSS): an ordinary chapter row's cluster is narrow enough to stay beside the title even at the ~630 px card width three columns leave; only a wider cluster (the `retail-sample` state's tag) exceeds 640 px and wraps, exactly the row the old assumption clipped.
3. **A same-property variant must stay in one Tailwind "bucket."** Tailwind v4 orders every arbitrary `min-[Npx]:` variant's `@media` block together, sorted by width, but emits the named scale's blocks (`xl`, `2xl`, ...) as a separate, later group regardless of the actual pixel value. Two variants on the same property (here, `grid-template-columns`) must therefore both be arbitrary or both be named, or the named one's later block wins the cascade even at a width where the arbitrary one's condition also matches and is numerically smaller - found empirically when `xl:grid-cols-[...]` (1280 px, named) kept overriding `min-[1440px]:grid-cols-[...]` (arbitrary) at 1440 px and above, silently keeping the page at two columns. Point 1's move of the two-column breakpoint to `min-[1280px]` is this fix, not a stylistic choice.

## Consequences

- Matches D85 exactly: the desktop capture (1440 px, `apps/ui/tests/visual/viewports.ts`) now shows three columns, as mock 02 draws them.
- The reader card's header is more correct than before this decision, not just for Script: a container query describes what actually determines the header's layout (the card's width) in every place `ReaderCard` renders (`ScriptPage.tsx`, `CreditsEntry.tsx`), including future ones, instead of a viewport number that only happened to hold while every consumer's reader was full width.
- A future page or panel that renders `ReaderCard` at an unusually narrow width will see its header stack correctly without needing its own breakpoint math - the container query is the source of truth.
- The Script page's outer grid, and any future `apps/ui` layout mixing a named Tailwind breakpoint with an arbitrary one on the same property, must watch for the bucket-ordering pitfall in point 3. A later change to the reader column's own breakpoints should keep both grid-cols variants in the same bucket.
- `tests/visual/drivers/shared.ts`'s `selectReaderWord` now scrolls the matched words into view before selecting them (a real narrator only ever selects visible text; the programmatic selection did not, and a taller stacked header above the target chapter could otherwise select text below the fold, placing `SelectionMenu`'s viewport-anchored popup off-screen too) - a test-infrastructure fix this decision's own verification found necessary, not a change to `SelectionMenu` itself.
