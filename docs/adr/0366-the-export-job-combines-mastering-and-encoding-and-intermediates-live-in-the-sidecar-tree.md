# 0366. The export job combines mastering and encoding, and intermediates live in the project's sidecar tree

**Status:** Proposed
**Date:** 2026-09-27
**Supersedes:**

## Context

[render-encode-master.prd.md](../prds/render-encode-master.prd.md) Phase 5 wires the Master & QC export flow's bindings and UI over three already-delivered, binding-free pieces: `internal/mastering.Master` (Phase 3), the `Encoder` port's `ffmpeg` row (`internal/encodeport`, Phases 1-2) and `internal/packager.Assemble` (Phase 4). The PRD's own Architecture section sketches four bindings by name — `EncodeStart`, `EncodeCancel`, `MasterStart`, `PackageAssemble` — as a description of the work, not a frozen API; Phase 5 is where the exact shape is decided. Three questions had no existing answer:

1. Does mastering get its own job and its own Start/State/Cancel bindings, separate from encoding, or do they share one?
2. Where do a mastered WAV and an encoded file live before they are packaged — they are not the narrator's deliverable (the package is, Q5), but they are not nothing either?
3. Does `PackageAssemble` report progress the way the encode/master job does, given `packager.Assemble` (Phase 4) has no progress callback of its own?

## Decision

**One job, not two.** `ExportStart`/`ExportState`/`ExportCancel` master (when asked) and encode every picked item in one job, per file, in that order. The user flow (this PRD's own "Solution Detail" and the concept mock's "MASTER ALL TO SPEC…" button) is already one narrator action — "Master & encode" — not two separate ones a narrator would run back to back; a second job kind for mastering alone would need its own progress plumbing, its own wire contract and its own UI section for no capability a narrator could not already get from a toggle (`master: bool`) on the one job. `internal/mastering.Master` and the `ffmpeg` `Encoder` row are still called through their own ports, unmodified by this choice — it is a host-side composition, not a change to either port's shape.

**Mastered and encoded files are scratch, not deliverables, and live under `<project>/narration-utils/render-encode-master/{mastered,encoded}`.** Q5 already decided the *package* is the narrator's deliverable and lands outside the sidecar tree, in a folder the narrator picks. An intermediate the export job writes on the way there is derived data the same way a proofing render fingerprint or a chapter-sync watcher's state is (`internal/proofing`, `internal/chaptersync`, both already under `narration-utils/`) — the narrator did not ask for these two files to exist, only for the final package. Keeping them in the sidecar tree means a second export run cannot collide with a narrator's own files, and `packager.Assemble`'s own "never overwrite" rule only has to reason about the one folder the narrator chose for the package.

**`PackageStart` is an async job (`PackageState`, `PackageCancel`) with no internal progress, unlike `ExportStart`.** ADR 0075's 100 ms acknowledgement rule is why it is a job at all — `packager.Assemble` copies files (already-encoded, hence small, unlike the raw WAVs the export job reads and writes) and could in principle run long enough to matter for a very large book, so the call that starts it must return before the copying is done. But `Assemble` itself takes no progress callback (Phase 4 did not need one for its own Go tests), and adding one now would be a change to an already-delivered, already-tested port for a UI-only need; `PackageState` instead reports `running` with no percentage until the goroutine finishes, the same "known but not measured" honesty the app already uses elsewhere for a step with no finer-grained signal.

**A package item's `kind` is a plain wire string, not `apps/desktop/internal/packager.Kind`.** The Go type is a `type Kind string` with four constants; wiring it through unchanged makes Wails generate a TypeScript `enum` for it, which is not structurally assignable from a plain object literal the way every other request the UI already builds is — every binding call in the app passes a literal object, never a class instance. Every wire struct that carries a `packager.Kind` (`ExportItem`, `ExportFileResult`, `PackageItem`, `PackageManifestFile`) declares `Kind string` instead and converts at the boundary (`string(packager.KindChapter)` out, `packager.Kind(item.Kind)` in); the Go-side ports still use the real enum type everywhere else.

## Consequences

- **One less job kind to keep in sync.** `jobKindRenderExport` covers both mastering and encoding; a future phase that wants mastering exposed on its own (there is no such request today) would need a real reason, not just symmetry with `EncodeStart`/`MasterStart` as the PRD's Architecture section first sketched them.
- **The export job's percent is a two-stage estimate, not measured bytes throughout.** With mastering on, each file's weight is split 50/50 between its mastering and encoding stages (`weightRemaining`); this is close enough for a progress bar and matches the same "never move backwards" contract every other host job's percent already promises, but a narrator reading the exact number mid-file should not expect it to track bytes precisely across the stage boundary the way `internal/mastering.Master`'s own multi-pass tracker does internally.
- **A crashed or killed app can leave orphaned files under `narration-utils/render-encode-master/`.** Nothing here cleans them up between sessions (mirroring how the project's other derived folders are not swept either); a stray file there is scratch, never read back as the narrator's own data, and a future phase can add a cleanup step without touching this ADR's decision.
- **Changing this decision.** Splitting the export job into two, moving the intermediates outside the sidecar tree, or giving `PackageStart` real per-file progress (which would mean changing `packager.Assemble`'s own signature, an `internal/packager` change, not just a binding one) is a new decision: write a new ADR in lane U's block (0360-0379) that supersedes this one.
