# 0343. A Story Bible entity keeps its id by name overlap across a rebuild, and dialogue cues are precision-first rules

**Status:** Accepted
**Date:** 2026-09-27

## Context

`docs/prds/character-continuity-review.prd.md` Phase 2 ("Stable characters, dialogue cues, appearance maps") was previously flagged on `#509` as undeliverable from lane A, since its scope is centered on `sidecars/manuscript-guide/core/manuscript_guide.py`, which the implementation plan's lane table assigns to lane B (ADR 0263's closing note; PR #605). This ADR records the phase's design decisions, delivered by lane B (stream N-B25).

The PRD's own Evidence section left two things explicitly unverified: whether an unlocked, generated character keeps its id across a rebuild (it does not, as built - `entity_id()` hashes whichever spelling `build_entities` currently picks as `canonical_name`, and that pick can change between builds, e.g. when a title-prefixed mention such as "Captain Arelian" first joins a group that previously only ever saw the short form "Arelian"), and how dialogue lines should be attributed to characters (Q4).

## Decision

**Stable ids (the PRD's own open TBD).** `merge_locked` no longer matches a freshly generated entity to its predecessor by exact id alone. It first tries the exact match (unchanged, and still how a locked or manual entity is found); when that misses, it looks for any previous entity whose name set (`entity_name_keys`: the normalized canonical name plus every alias) overlaps the fresh entity's own name set, reclaims that previous entity's id, and proceeds exactly as an exact-id match would (locked/manual entities kept wholesale; otherwise the narrator's reviewed fields carried forward). Each previous id is claimed at most once per rebuild, so two previously distinct entities are never silently folded into one just because a fresh build's hashing happens to line up with the wrong entry. This makes an entity's identity track *what the narrator has been reviewing*, not an artifact of which spelling a particular build's extraction happened to pick as canonical.

**Alias split.** `split` is the inverse of the existing `merge`: it removes one alias from an entity and gives it a fresh, standalone entity of its own, and clears any `absorbed_names` entry for that spelling so `merge_locked`'s redirect step (which exists to keep a `merge` from being silently undone by the next rebuild) does not immediately fold the split entity back into its former parent.

**Chapter and scene appearance maps.** A paragraph made only of break punctuation (`***`, `- - -`, `# # #`, a bullet or dash) is a scene break (`SCENE_BREAK`): it is not itself part of either scene it sits between, and scene numbering restarts at 0 for each new chapter. Every entity carries `appearances`: the distinct (chapter, scene) pairs its evidence (canonical name and every alias) touches, in reading order. This is additive JSON, normalized the same defensive way `apps/desktop/internal/guide/service.go`'s `normalizeEntity` already treats every other array field (missing reads as empty), and described in the TypeScript contract (`apps/ui/src/api/contracts/storyBible.ts`'s `GuideAppearance`) and its Zod schema, though nothing consumes it yet - that is Phase 6's job, the same "no bindings until the UI needs them" precedent ADR 0263 set for Phase 3.

**Dialogue cue extraction (Q4, option A, as the PRD recommended).** `extract_dialogue_cues` finds double-quoted spans and attributes each to a known Character (never a Place or Organization) only when a speech verb (`SPEECH_VERBS`, deliberately narrower than the existing `PERSON_WORDS` proximity set used for entity classification) sits next to a name or alias already in the Story Bible, immediately before or after the quote. A quote with no such tag is checked for per-scene continuation: when exactly two characters are already active speakers in that scene, an untagged quote alternates to whichever of the two did not speak last. Everything else - no tag, three or more active speakers, only one established speaker, a name that never became a real Character entity - stays `unknown` rather than guessed at, matching ADR 0020's precision-over-recall stance and the PRD's own risk note that wrong attribution creates false drift flags. Pronoun tags ("she said") are out of scope by design, the same boundary Q4's recommendation drew around "quote spans, adjacent 'said Name' and alias patterns" without pronoun resolution; the labeled-quote evaluation (`docs/research/character-continuity-cue-extraction-eval/RESULTS.md`) documents this explicitly, including the one case where two-person continuation still recovers the right speaker despite a pronoun tag, and the one case where continuation over-fires because a third speaker had not yet spoken at the point a line occurs - a known, accepted cost of a heuristic that cannot look ahead.

**Corrections survive a rebuild (mirrors ADR 0007).** A cue's id (`cue_id`) is a hash of its paragraph, its position and its own quote text, so it is stable across a rebuild that does not change that paragraph's text. `correct_cue` records the narrator's own attribution (or clears it back to `unknown`) and marks the cue `corrected`; `merge_dialogue_cues` carries a corrected cue's attribution forward by id on every rebuild, the same durability a locked Story Bible entity already gets, and a cue whose underlying paragraph text changed simply gets a new id rather than dragging a stale correction onto unrelated content.

## Consequences

- A character's reviewed history (description, personality notes, context, relationships, properties, a chosen pronunciation, hand-added aliases) now survives a rebuild even when the canonical spelling choice shifts - closing the PRD's own open TBD with a test (`test_an_unlocked_entity_keeps_its_id_when_a_title_prefixed_mention_first_appears`) rather than leaving it unverified.
- Phase 5's candidate locator and Phase 6's review UI can distinguish a directly tagged cue from a continuation-sourced one (`speaker_source`) and treat them with different confidence, which the labeled-quote evaluation shows matters: continuation is right far more often than not, but not always.
- Nothing in this phase changes the Story Bible page's behavior: no binding reads `appearances` or `dialogue_cues` yet, so the existing UI is unaffected (verified by the existing Story Bible component tests staying green).
- A future phase that wants broader coreference (resolving "she said" to the most recently named character) or a smarter continuation rule (aware of a scene's full cast, not just speakers established so far) should write its own ADR if it changes the behavior recorded here, rather than silently loosening precision-first extraction.
