# 0485. A native take's line identity lives in a project-owned sidecar file, mirroring but not sharing code with ADR 0026

**Status:** Accepted
**Date:** 2026-09-28
**Supersedes:** none (extends [ADR 0026](0026-manuscript-line-identity-in-item-extension-data.md) and [ADR 0098](0098-take-provenance-in-take-extension-data-extends-adr-0026.md) to a source with no REAPER item at all; neither is superseded)

## Context

`docs/prds/native-recording-suite.prd.md` Phase 3 ("Take contract and identity") needs a line-identity scheme for native takes recorded by the built-in recorder (Phase 2, [ADR 0455](0455-the-built-in-recorder-records-each-take-to-a-partial-file-in-the-projects-recordings-folder-and-links-it-to-its-take-name.md)), so the review pipeline (duplicate/pickup detection, character continuity, diagnostics) can tell which manuscript line a native take belongs to, the same way it already can for a REAPER-recorded one. Open Question 8 of that PRD asked this directly and the owner answered it (D86, 2026-09-28): "a line-identity scheme from day one, as a metadata file keyed by take, designed in Phase 3 together with the take contract."

REAPER solved the equivalent problem by writing a namespaced `P_EXT:narration_utils_line_id` key onto the item itself ([ADR 0026](0026-manuscript-line-identity-in-item-extension-data.md)), later extended to take-level provenance the same way ([ADR 0098](0098-take-provenance-in-take-extension-data-extends-adr-0026.md)). Both ADRs reject a sidecar file explicitly, because a sidecar drifts whenever the narrator moves, splits, or copies REAPER items and nothing keeps it in sync - extension data travels with the item, a sidecar does not.

That reasoning does not carry over to a native take. A native take is a WAV file in the project's `Recordings/` folder (Q4, D86); it has no REAPER item, so there is nothing to attach extension data to, and nothing that could split or copy it out from under a sidecar the way a REAPER item can. A native take file, once finished, is never overwritten, edited or renamed in place ([ADR 0455](0455-the-built-in-recorder-records-each-take-to-a-partial-file-in-the-projects-recordings-folder-and-links-it-to-its-take-name.md), Q5): its name is stable for the file's whole life, so a sidecar keyed by that name cannot drift out from under it the way ADR 0026 was worried about.

## Decision

`apps/desktop/internal/recording/identity.go` stores a native take's line identity in `<project>/Recordings/line-identity.json`, a JSON object mapping take name ("Take 004") to a composed line id. The id itself is composed and parsed by `recording.ComposeLineID`/`recording.ParseLineID`, which mirror `internal/lineidentity.ComposeLineID`/`ParseLineID` field for field: the manuscript entity id (a paragraph id such as `p-000001` or a chapter id such as `c-0001`) plus the manuscript's current source SHA-256, joined by `@`. The two packages deliberately share no code - `internal/recording` stays free of any REAPER/`dawport`/`manuscript` dependency, matching its existing header comment ("Nothing here knows about WASAPI: the row does") - only the wire scheme, so a line id composed by either path parses identically wherever it is read. `recording.Service.SetTakeLine` assigns or clears one take's identity; `recording.Take.LineID` (the composed id, or nil) is read back by `listTakes` on every snapshot and rides the existing `recording:state`/`RecorderState` wire payload, so no new Wails binding was needed to expose it for reading.

Writing the identity happens only through `Service.SetTakeLine`, which never touches the take's audio file - the same rule Phase 2 already keeps for the file itself (Q5). No caller wires narrator-facing UI to it yet: assigning a take to a manuscript line is Phase 4's job (take review integration), explicitly out of this phase's scope; Phase 3's job is the contract and the identity scheme, proven by tests, not the UI that will call it.

A native take's `findings.Source` (`recording.Take.Source()`) carries only `File`; `TrackGUID`/`ItemGUID`/`TakeGUID` stay empty rather than a synthetic stand-in. The findings contract already documents those three fields as "optional REAPER track, item, and take GUIDs" - REAPER-specific extras, not a generic DAW-neutral identity slot - so populating them with a fabricated value would misrepresent a native take as one REAPER-navigation code (`FindingsGoTo`, `FindingsLoop`) could resolve inside a running REAPER. Leaving them empty is what "no REAPER item exists" already means everywhere else in the contract.

## Consequences

- A native take's line identity survives everything ADR 0026 worried about for REAPER items (a move, a rename attempted by something other than this app) simply because nothing in this codebase renames or moves a finished take file; it does not need item-level durability because it was never exposed to item-level instability.
- `internal/repeats.ToFindings` (the take-review scan's adapter) already accepts a `Member` with no `ItemGUID`/`TakeGUID` and produces a valid finding from it (`internal/repeats/native_source_test.go`), but its finding-id and evidence-version keys still lean on those REAPER-only GUIDs for uniqueness between reads; without them, two native reads that share an offset and length are not distinguished. Nothing in the codebase constructs a GUID-less `Member` today (`internal/takereview` only ever reads a REAPER `tracks.Project`), so this is not yet reachable in production. It is recorded in `adapter.go`'s `memberKey` doc comment and left deliberately unfixed here: closing it would also reshape every existing REAPER-sourced take-review finding's id and evidence version, silently orphaning narrators' stored review decisions for evidence that never changed (`docs/architecture/findings-contract.md`: "a decision survives … a re-run with unchanged evidence"). Whoever wires native takes into the take-review scan (a later phase) should settle a stable per-member native identity (the take's own file name is a candidate, since Q4/Q5 already make it stable and never reused) before that key changes.
- A narrator who wants a native take's line assignment has no UI to set it yet; `Service.SetTakeLine` is ready for Phase 4 to bind.
- Moving native line identity to a different home (item-adjacent metadata of some kind, were one ever added) would need a new ADR superseding this one, for the same reason ADR 0026 gives for its own scheme: the two packages intentionally never got coupled, so nothing here assumes the sidecar's shape stays canonical - it just needs to keep round-tripping through `ComposeLineID`/`ParseLineID`.
