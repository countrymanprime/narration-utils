# Design system reference

**Status: living document — describes current state, not a point-in-time decision.** Each entry links back to the ADR that justified it. Unlike `docs/adr/`, this file is meant to be edited as the system evolves; the ADRs underneath it are what stay immutable.

## Tokens

Design tokens are CSS custom properties defined in `apps/ui/src/styles.css`'s `:root` block, with dark-mode overrides in a single `:root[data-theme='dark']` block. New Tailwind-based components reference them via arbitrary-value syntax — `bg-[var(--surface)]`, `border-[var(--border)]`, `text-[var(--text-muted)]` — rather than duplicating values into `tailwind.config.js`. See .

Key tokens: `--bg`, `--surface`, `--surface-2`, `--surface-3`, `--border`, `--line-strong`, `--btn-line`, `--focus`, `--text`, `--text-muted`, `--non-text`, `--accent`, `--accent-strong`, `--accent-soft`, `--accent-contrast`, `--danger`, `--character`/`--place`/`--org`/`--review` (category colors), `--backdrop` (modal/drawer scrim), `--shadow`, `--shadow-lg`. `--space-*`/`--font-size-*` are additive spacing/type-size steps, grounded in values already repeated across the file — not a full scale, for new/touched code to converge on rather than picking another one-off rem value. `--z-*` is the one layer scale (`styles.css`, order pinned by `layers.test.ts`): `panel-scrim` 19 and `panel` 20 (a Script drawer, under the rail), `nav` 30, `takeover` 40, `slide-over-scrim` 45, `slide-over` 50, `popover` 55 (menus, context menus, anchored popups), `dialog` 60, `dialog-popover` 70, `toast` 80 (portalled to `<body>`, so a toast raised from a dialog or slide-over is drawn above it), `tooltip` 1000. A component names a layer with a token and never a bare number; a page panel is drawn inside its page (absolute), never fixed to the window, so it cannot cover the rail.

**Colour meets WCAG AA** ([Colour and contrast](colour-and-contrast.md); the rules, the token table, how to choose a colour and how the guard works are in [colour-and-contrast.md](colour-and-contrast.md)): there are two text levels, `--text` and `--text-muted`, and one colour for what is seen and not read, `--non-text` (icons, dots, glyphs). `--text-faint` no longer exists. Status text uses `--danger-text`, `--warn-text` and `--info-text` (`--danger`, `--warn` and `--info` stay for borders, dots and fills); the current navigation item is `--accent-strong`; highlights and entity badges draw `--<kind>-text` on a tint of the kind colour, and the eight kind colours have dark values. Placeholders are `--text-muted`. `apps/ui/src/paletteContrast.test.ts` holds every declared pair to 4.5:1 (text) or 3:1 (marks) in both themes.

## Which mocks are the spec

The Studio Next mock (`docs/research/mockups/studio-next/`) is the spec for every page it covers: its layout, tokens, primitive sizes and behaviour (owner ruling D98, 2026-10-11). Where an older ADR, a benchmark mock or a value in this page differs, the mock wins. When a primitive, token or style does not draw what the mock shows, the primitive changes and every page inherits it; a page does not restyle it locally. The full rule, including what is not built and what stays as built, is in the Studio Next rebuild PRD's "Which mocks are the spec" section.

## Theme

The theme is one app-wide setting, light or dark (owner ruling D69). No page or surface forces light or dark, and a dark mock shows the dark theme, not a per-page look; the booth no longer forces dark ([Derived and status tokens](colour-and-contrast.md#derived-and-status-tokens)). `data-theme` on `<html>` is set by `ThemeProvider`/`useTheme` (`apps/ui/src/theme/`), a tri-state Light/Dark/System preference persisted to `localStorage`, exposed via a new "Appearance" category in `Settings.tsx`. An inline bootstrap script in `index.html` sets the attribute before first paint to avoid a flash of the wrong theme. See Theme.

## Primitive components

Location: `apps/ui/src/components/primitives/`.

**The component atlas is the source of truth for what each primitive can look like.** Every primitive has a `<Name>.stories.tsx` next to it (one story per variant/state, `play()` for the primary interaction). Browse it with `pnpm --dir apps/ui storybook`; `pnpm --dir apps/ui atlas` builds it and captures every story in light/dark at a wide and a narrow viewport, failing on axe violations, a throwing `play()`, sideways overflow, or console errors. `src/atlasCoverage.test.ts` fails if a primitive has neither a story nor a recorded exemption, and `src/stories.test.tsx` runs every story as a unit test. ### Navigation shell

`AppShell.tsx` draws the rail and the top bar at the benchmark mocks' measured sizes: a 216 px rail (`--surface`), a 62 px brand block over a divider, 37 px nav-item pitch with a selected item ≈198×34 inset 8 px (`--accent-soft` fill, `--accent-strong` label), and a 52 px header with `HeaderChip`s 12 px apart, 20 px from the edge. ### Native controls stay in the primitives

A page builds a control from a primitive and never writes the native element. `apps/ui/src/rawNatives.test.ts` counts the native `button`, `select`, `input`, `textarea` and `table` parts written in JSX outside `components/primitives/`, and fails on the pasted icon-button look (`size-8` with `rounded-md`). Use `IconButton` for an icon-only button, `Button` for a text button, `TextField`, `SearchField` or `Field` for a text control, `NumberInput` for a number, `Select` for a choice, and `Table` for tabular data. Two things let a native element stand:

- **A marker.** A comment `native-control-ok: <reason>` of at least 12 characters on the element's first line or the line above leaves it out of the count, whatever its tag. The reason says what the element does that no primitive can. A marker with no native element under it is stale and fails.
- **A ceiling.** A per-file count that may only go down: a count above it fails, and so does a ceiling above the real count, so the entry is lowered or deleted in the change that removes the element. `select`, `textarea` and the table parts have none left; `button` has the most, and `input` is kept for three hidden file pickers.

`ZERO_DIRS` lists the folders built to the Studio Next mock (the schedule, readiness and pipeline folders so far). A native element there needs a marker or a primitive, a ceiling there fails, and a listed folder that no longer exists fails. A page swap adds its new folder to `ZERO_DIRS` and deletes the old page's ceilings in the same PR. A ceiling is therefore not the only escape: a marker is the way out for a new element no primitive draws, and a ceiling only records old debt.

### Import rules

Three import facts are checked, not reviewed ([Verification and code-health tooling](../operations/verification-tooling.md), `pnpm --dir apps/ui architecture`): a file in `components/primitives/` (a story or a test too) imports nothing else under `components/`, so shared data such as the chapter status labels sits above the feature folders (`src/chapterStatus.ts`); only `src/api/` imports the generated `wailsjs/` bindings and the Wails runtime (`@wailsio/runtime`, [ADR 0001](../adr/0001-the-app-is-written-in-go.md)); and only a primitive imports Base UI. `Highlight` is the only file that writes a `<mark>`, with one reasoned exception, the Script reader's Find bar match (the proofing diff's `InlineDiffRow`, the subject of , was deleted with the chapter workspace); `src/highlightBoundary.test.ts` is the check.

### Base UI wrappers

Interactive behaviour (focus trap, Escape, focus return, id wiring, roving focus) comes from Base UI (`@base-ui/react`), and only the primitives import it. To build a widget:

- **One flat file per primitive** in `primitives/`, with a `<Name>.stories.tsx` and a `<Name>.test.tsx` next to it (a multi-part primitive, `Tabs`, `Table`, `Collapsible`, keeps its parts in one file). A primitive that is only the browser's own element with our tokens (`Select`, `Table`) uses no library part. Import per component (`@base-ui/react/dialog`), never the package root.
- **A closed API.** Keep the props call sites already use, add only explicit new ones, never spread Base UI props and never export a Base UI type. `className` and standard DOM attributes are fine. A part that renders a button is composed with our `Button` through `render`.
- **Style with Tailwind and tokens only:** `var(--token)` values and data-attribute variants on the parts (`data-open:`, `data-starting-style:`, `data-disabled:`, `data-invalid:`), mutually exclusive states, no new class in `styles.css`, none of the library's example CSS.
- **Focus rings.** A primitive draws no focus outline of its own: the global `:focus-visible { outline: 2px solid var(--focus); outline-offset: 2px }` rule in `components.css` applies (the Studio Next mock's rule). Where a clipped scroll area or a grid cell cannot show an outside outline, the primitive keeps an inset ring or a negative offset, still coloured `var(--focus)` (`Dialog`, `SlideOver`, `WorkDialog`, `StageGrid`, `Table`, `Timeline`); `primitives/focusRing.test.ts` fails a primitive that names `--accent` for focus.
- **Stacking.** `#root` and the Storybook decorator are `isolate`, so a popup portalled to `<body>` is outside the app's stacking context and always above it. The numeric order among popups is slide-over 50, dialog 60, selection menu 65, nav drawer 70, tooltip and popover 1000.
- **Prove behaviour in a story.** A keyboard behaviour (Escape, Tab trap, focus return) is a `play()` in the wrapper's story, checked in the Chromium atlas; `stories.test.tsx` runs the same story in jsdom, which needs no polyfill for Base UI. Stories find portalled popups on `document.body`, not inside the story canvas.
- **The boundary is a test.** `src/baseUiBoundary.test.ts` fails on any `@base-ui/*` import outside `primitives/`, so a page that needs a new behaviour gets a new primitive first.
- **Bundle budget.** The production JS bundle (`apps/ui/dist/assets/index-*.js`) was 571,969 bytes raw (158,239 gzip) before Base UI, 787,619 raw (231,679 gzip) with every wrapper of the foundation stack, and 794,295 raw (237,296 gzip) with the native-control, tab, toggle-group, tag-input and table primitives (CSS 44,244): +38.9% over the start. At the Studio UI Primitives close-out, after the work landed alongside it (the DAW port, provider ports, input commands and the ten studio primitives), it measured 1,363,668 raw (401,962 gzip, CSS 75,553): +138.4% over the start, past the budget below. The growth is spread across the feature code landed since the previous measurement, not concentrated in the ten flat leaf files those primitives added. The budget is **800,000 bytes raw**, a documented number and not a CI gate: a change that takes the bundle past it (a Base UI minor bump, a new family) says why in its pull request; the bundle already being over it is a standing note for the owner, not a reason to block a change that doesn't grow it further. Measure with `pnpm --dir apps/ui build` and look at `dist/assets`. It is a desktop app served from disk, so the cost is parse time, not download.
- **What is not wrapped.** The alias combobox in `GuideDetail.tsx` (domain matching and an active index; its input is a `TextField`), `Button`, `NavButton`, `Heading`, `Panel`, `Highlight` and `ErrorBoundary` are plain components with no library part; a page that needs a new widget gets a new primitive.

The custom-CSS system (`.btn`, `.panel-head`/`.panel-body`, `.progressbar`, etc.) that was deliberately left in place for not-yet-migrated consumers has since been fully migrated to Tailwind utilities. New UI work should reach for Tailwind utilities directly rather than adding to `styles.css`. The [Base UI wrappers](#base-ui-wrappers) section also lists the small set of deliberate exceptions still in `styles.css` (scrollbar-hiding rules, keyframe animations, and a handful of unstyled "marker" classes kept only because visual/unit tests select by CSS class; the generic `table.dtable` style was the fourth and is gone, replaced by `Table`).

## Conventions

- **Numeric table columns are right-aligned** (`align="right"` on the `TableHeader`, `numeric` on its `TableCell`s) — see `DiagnosticsTables.tsx` (Delivery's diagnostics) for a reference implementation.
- **Disabled interactive elements never show a hover affordance.** Use `disabled:pointer-events-none` (Tailwind) alongside `disabled:opacity-*`, not just the opacity change alone — a hover transform/background change that still fires on a disabled element reads as clickable when it isn't.
- **A field that is read-only, locked or not-yet-persisted is `disabled`, not hidden**, so the user can see what exists without being able to edit it. Story Bible entries open read-only and gain Edit/Save/Cancel controls only on request ([Story Bible](../guides/using-the-app/story-bible.md)); see `GuideDetail.tsx`.s `editingDisabled`.
- **A non-destructive "peek at something else" action is a `SlideOver` primitive, never a navigation that replaces the current view's state.** See `script/ScriptPage.tsx`'s Chapters & Search overlay and `GuideDetail.tsx`'s "Review entry" overlay — both exist specifically so switching context doesn't discard an in-progress edit.

## Layout and scrolling

The document (`html`/`body`) never scrolls; it is locked (`overflow: hidden`, `styles.css`) once nothing needs it to. Every page scrolls inside the shell's own page area (`AppShell.tsx`'s `<main>`, `.scroll-chrome-hidden`), which is the shell's single scroll container and also gives absolutely positioned descendants (an `sr-only` label, a Base UI hidden input) a containing block so they scroll and clip with their row instead of escaping to the window. Before a project is attached, `StartupScreen` and `ProjectPicker` scroll in the same way inside their own `flex-1 overflow-y-auto` container, with `DemoBanner` above it in a `flex h-full flex-col` so the banner's own height never pushes the document past the viewport. The shell is sized off a `height: 100%` chain from `html`/`body`/`#root` (`h-full`), not `100vh`/`100dvh`, because only the `%` chain stays exact under both WebView2's zoom and a CSS `zoom` on `<html>`.

## Layout rules

Four widths and the rail decide the layout, as the Studio Next mock lays it out:

| Class | Applies | Meaning |
| --- | --- | --- |
| `railCollapsed` | below 1360 px | The rail shows icons only. The editing timeline strip sits under the script from 1360 px (`STRIP_MIN_WIDTH`) and is part of the drawer below it |
| `medium` | 1280 px and below | Busy side columns become drawers or stack. This is the one inclusive bound |
| `narrow` | below 1180 px | Narrow layouts |
| `tiny` | below 860 px | Tiny layouts |

**Where they live.** `apps/ui/src/layoutBreakpoints.ts` holds the numbers, `layoutClassFor(width)` and `LAYOUT_QUERIES`, one media query per class. `useLayoutClass()` (`src/hooks/useLayoutClass.ts`) follows those queries for the places CSS cannot decide, and returns the full layout where there is no `matchMedia` (jsdom). Tailwind cannot read a constant inside a class name, so a page writes the width variants out: `min-[1360px]`, `max-[1359px]`, `max-[1280px]`, `min-[1281px]`, `max-[1179px]`, `min-[1180px]`, `max-[859px]` and `min-[860px]`. `src/layoutQueries.test.ts` scans the source, fails a variant between 860 and 1440 px outside that list unless the file's count is recorded in `OFF_VOCABULARY` (counts only fall), and fails a width compared with one of the four numbers outside the hook. The scan, not an import, links the classes to the module.

**Zoom.** The rules read the reported CSS width, not a zoomed one, so host zoom moves a window across a band: a 1440 px window at 200% reports 720 px ([Zoom](../guides/using-the-app/navigation.md#zoom)). The mock's `style.zoom` mechanism is not used.

**What the visual suite draws.** The matrix is 1440, 1024 and 768 px. Two bands it would miss are drawn by rows that opt in with `LAYOUT_BANDS`: 1300 px (rail collapsed, not yet medium) and 1230 px (medium, not narrow). The 390 px reflow width is for rows that opt in with `extraViewports`. There is no phone viewport ([viewports.ts](../../apps/ui/tests/visual/viewports.ts)).

## Settings rows

`apps/ui/src/components/settings/ScopedSetting.tsx` renders one Settings field by its `kind`, and the host (`apps/desktop/app.go`, `fieldSchemas` and `validateSettingValue`) validates it by the same kind. Every value is a string in the settings files.

| Kind | Control | Stored value |
| --- | --- | --- |
| `choice` | `Select`, full width of its column | one of the schema's choices |
| `text` | `TextField` | any string |
| `color` | a colour swatch and a mono hex `TextField` on one line | six hex digits, no `#`, capitals |
| `bool` | `Switch`: the row is the switch (named by the setting), its hint icon and Reset, not a label column and a control column | `"true"` or `"false"`; anything else reads as off and the host rejects it |

**Layout.** Below `md` (768 px) the label stacks above the control; from `md` to `lg` the label column is a fixed 12rem, from `lg` `minmax(12rem,16rem)`. A grid gives a fixed-range track its full maximum before a flexible one gets any, so a two-column template with no breakpoint left a 45 px control at a 390 px window (defect 8, [Visual bug fixes require screenshot verification](../../.claude/rules/ui-visual-verification.md)). Selects and text boxes take the free width (`flex-[1_1_10rem]`, `min-w-0`) up to `max-w-md`, so every select is the same width; the hex box has a 4.5rem minimum beside its swatch; the control row wraps, so Reset shares the line and drops under the control only when there is no room (it does at 768 px). Tailwind utilities on tokens only; no primitive or `styles.css` change.

**Saving.** A panel's form holds every field of its settings tool, and a field with no value in the scope is an empty string, which the host rejects for a choice or a colour. Save sends only the fields whose value changed (`changedValues` in `settings/page/ScopedFieldsPanel.tsx`); putting a field with no value of its own back to the value it inherits is no change, and a save with nothing changed does not call the host.

**Adding a field.** Add it to `fieldSchemas` (Go) and give it a default in `config/defaults.json` and in `builtinDefaults` (`internal/settings/store.go`; a test keeps them equal) and in `mockFixtures.ts`. It needs no visual-suite work unless it is a new panel, which is a new `settings` catalog row with `...REFLOW`. The suite then checks the row at 390 px: a text box or select narrower than 64 px fails, and the PNG at `screenshots/app/settings/<state>/reflow.png` is one to look at with the other viewports. The first `bool` field also needs its own state so the Switch row is captured; none ships yet (the notification and Build Story Bible after import settings, are the first).

**Local assets.** The Local assets panel is a list, not field rows: one `li` per asset (`apps/ui/src/components/assets/LocalAssetRow.tsx`) in the `surface-2` block look of the other Settings panels, with the asset name as a level-3 heading under the panel's level-2, its facts as a definition list that wraps, a `ProgressBar` while it downloads, one live region (`role="status"`) for progress and results, a failure as `role="alert"` in the row, and its actions in a wrapping row at the bottom so nothing collapses at 390 px. Its buttons are named with the kind and the asset ("Verify Whisper model Small"); the one action slot keeps its place as the state changes (Download, then Cancel, then a pending Verifying, then Verify) so keyboard focus is not dropped. It has no text box or select, so the collapsed-control check has nothing to measure; it is still captured at the reflow width like every Settings state.

**Known at 390 px, outside Settings** (found by a one-off sweep of every state at that width; the collapsed-control check passes everywhere): the Proofing results header and table (#148), the Home chapter table (#149) and a three-action confirm dialog (#150) are clipped or cramped. They need layout decisions and are reachable only by zoom, since the shell's minimum window is 960 px.

## Manuscript reader

- **One card per section.** Each chapter starts with the mock's boundary: a dashed "End of … · N words" line, then `ChapterCard` (`apps/ui/src/components/script/page/chapters/ChapterCard.tsx`, not a primitive) with the label, Record in Booth, the title, the facts line and My prep. The opening and closing credits are drawn the same way by `CreditsSection.tsx` beside it, as the mock lists them as chapters, with their own prep state; their unresolved tokens and Fill in sit in the card's banner row. There is no disclosure: every section's text is always shown.
- **Read time** (`readTimeLabel` in `apps/ui/src/state.ts`) is shared by every card: seconds under a minute (`~2 s read`), minutes at and above it (`~16 min read`) — the same 200 words/minute figure a chapter always used, just no longer rounded up to "~1 min read" for a short credits segment.
- **Credits follow the reader**: the credits text is drawn in the reader's own font, size and spacing, one row per line, with an unresolved token highlighted in brackets. Find does not search it.
- **Alternating rows.** Paragraph rows alternate between `--surface` and `--row-alt` (a touch darker in light theme, a touch lighter in dark) with a 1px `--border` line between rows, like banded table rows. Highlights tint with `transparent` mixes so they read on either row.
- **Highlights** are the `Highlight` primitive only: entity, note and review share one look, filling the full line height, tinted and underlined in the kind's color and drawn in its derived `--<kind>-text` ([Colour and contrast](colour-and-contrast.md)).
- **Sticky chapter headers** are opaque (`bg-[var(--surface)]`) with a soft shadow once stuck; they must never be transparent over scrolling text.
- **"Go to line" target** stays highlighted (accent edge and tint) for 30 seconds (`JUMP_HIGHLIGHT_MS` in `script/ScriptPage.tsx`), with a brief ring pulse on arrival.
- **Formatting and line breaks** from import (`spans`, `\n`) render as `<strong>`/`<em>`/`<u>` and `white-space: pre-line` ([Manuscript import: formatting quirks and how they are handled](../architecture/docx-import-quirks.md)).
- **Side panels** use `SlideOver`; state-dependent classes are mutually exclusive.

## Chapter names

A chapter's name (its title and, when it has one, its subtitle) is drawn one way everywhere: **`Title — Subtitle`**, an em dash (space, U+2014, space), the title semibold and the subtitle `--text-muted` and regular, both in source casing — never CSS capitals, never italic, never monospace. A context prefix ("Read aloud", "Recording check", "Stage suggestion") uses `: ` instead, so the em dash only ever means "a subtitle follows" (`Read aloud: PROLOGUE — The Last Good Applause`, never `Read aloud — PROLOGUE — …`). `apps/ui/src/chapterName.ts` formats it as plain text (`full`, `short`, or `context(prefix)`); `TitleSubtitle` (above) draws it as markup, and the read-aloud reading heading (`ReaderText.tsx`) draws the same `stacked` convention by hand, since its title is per-word tracked markup, not a plain string - the subtitle sits under it, in view but not tracked. A source-scan guard (`apps/ui/src/chapterNameFormatting.test.ts`, in the style of `rawNatives.test.ts`) ratchets down every other read of `.subtitle` inside JSX or a template literal under `src/components/**`; a call site that still needs to show the second line on its own (not as part of a formatted name — a checkbox naming which line it is about, a search key) is not what the guard is for and stays off it. Migrated: the Manuscript chapter and credits card headers (`ReaderCard`), the Chapters & Search rows (`ChapterNav`), the import review's section rows (`ImportReview`), the Home chapter table (`AudiobookEstimatePanel`), the read-aloud dialog title and reading heading, the standalone Teleprompter's chapter select, and the Recording check and Stage suggestion dialog titles. Every other title-only site (a toast, a Tracks row, a Story Bible evidence row) still reads the bare title directly, which is already what `chapterName`'s `short` form would give it - no visible difference, so routing them through the formatter is follow-up, not a defect. The host and the sidecars follow the same rule through `apps/desktop/internal/chaptername` and `narration_common.chapter_names` (with a plain form, `Title - Subtitle`, for outputs that cannot take an em dash), pinned to `chapterName.ts`'s own `'plain'` form by `tests/fixtures/chapter-names.json` (`chapterName.fixture.test.ts` on the TypeScript side, [chaptername.go](../../apps/desktop/internal/chaptername/chaptername.go)). A REAPER chapter region's name, and so the render file name and the ID3 `CHAP` title that come from it, uses the same plain form.

## CSS layering gotcha

`styles.css` wraps only *some* rules in `@layer base`/`@layer components` (roughly lines 66–616); everything after that is unlayered plain CSS. Unlayered rules always beat Tailwind utilities (which live in the implicit `@layer utilities`) for the same property, regardless of source order. Before adding a Tailwind override next to a legacy class name, check whether that class is inside a `@layer` block — if it's unlayered, the Tailwind utility will silently do nothing for any property the legacy rule already sets.

**Same property, two widths.** Tailwind emits the named-scale media blocks (`xl:`) as a later group than the arbitrary ones (`min-[1281px]:`) whatever their pixel value, so a named variant overrides a narrower arbitrary one at wide widths. Two variants that set the same property at different widths must both be arbitrary or both be named; pages write widths as arbitrary `min-[Npx]` variants for this reason.

## Motion

See [`motion-and-animation.md`](motion-and-animation.md) — not yet a formal system. Motion is a `motion-safe:` utility (`ProgressBar`'s fill, `LevelMeter`, `Disclosure`, `Toast`), and `components.css` declares none (`apps/ui/src/legacyCss.test.ts`), because a legacy rule beats a utility in the same layer.

## What the suites do not prove

The visual suite is a gate on errors, not on appearance: it fails on page errors, failed requests, sideways overflow, a collapsed control (a text box or select under 64 px, [Visual bug fixes require screenshot verification](../../.claude/rules/ui-visual-verification.md); the Settings rows are also captured at a 390 px reflow width), blank screenshots and two states that render identically without a declared `sameAs`, and it says nothing about whether a layout looks right. Axe runs on Storybook stories in the atlas (`apps/ui/tests/atlas/atlas.spec.ts`) and on every app state in the visual suite: a violation fails the capture unless `apps/ui/tests/visual/axe-debt.ts` declares it with a reason, and a declared rule that stops being reported fails too, so the list only shrinks ([CI and releases](../operations/ci-and-releases.md); `UI_AXE=1` measures without failing). Aria snapshots pin the role trees of the dialogs, the slide-over and the navigation in a run of their own (`apps/ui/tests/aria`, [Verification and code-health tooling](../operations/verification-tooling.md)). None of this can judge gradients or low-contrast text over semi-transparent overlays, focus order or what a screen reader announces, so contrast by eye and a screen-reader pass remain. Pixel baselines are not adopted: the captures on one machine are now byte-identical from run to run (282 of 282 PNGs across repeated and CPU-throttled runs on the same Windows machine), which does not reproduce the earlier measurement (9 of 244 differing between two runs); but all of those runs were on one machine, nothing here shows that two machines or operating systems agree, and a baseline would have to come from a pinned Linux container. The spike that would decide this is [#153](https://github.com/countrymanprime/narration-utils/issues/153), after the suite has been stable for 50 runs, and its result is recorded as an ADR either way. The suite's own reliability rules (waits are conditions, `UI_CPU_THROTTLE` to prove a driver) are in [CI and releases](../operations/ci-and-releases.md#keeping-a-red-run-meaningful).
