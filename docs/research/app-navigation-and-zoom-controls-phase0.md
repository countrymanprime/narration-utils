# Phase 0: verifying today's back/forward and zoom behaviour on Wails v3

**Status: done, 2026-09-28.** Phase 0 of the [App Navigation and Zoom Controls PRD](../prds/app-navigation-and-zoom-controls.prd.md) (tracking issue [#547](https://github.com/countrymanprime/narration-utils/issues/547)), lane D. This settles what the PRD's own Evidence section could only infer from source before Phase 1 shipped, plus the four things Phase 0 names explicitly: which zoom gestures work, whether zoom persists, and whether the mouse's back/forward buttons and Alt+Left/Right navigate. No REAPER, no owner, per the phase's own scope.

## The question

The PRD's Phase 0 row: "Scripted Windows run of the v3 build: which zoom gestures work, whether zoom persists, whether mouse buttons 4/5 and Alt+Left navigate; record the result (the zoom mechanism is D29's `Window.SetZoom`)." Its Research Summary named four things "not done" because the packaged app had never been run: (1) whether Ctrl+=/-/0 do nothing (inferred from source); (2) whether a Ctrl+wheel zoom level survives a relaunch; (3) whether mouse buttons 4/5 navigate, and whether `preventDefault` stops them; (4) Alt+Left/Right (expected: nothing).

## Method

A throwaway scripted spike, `scripts/research/app-nav-zoom-p0-verify.ps1` (not wired into the shipped binary or any always-on CI job, the same status as `apps/desktop/cmd/spike-globalhotkeys`), run twice by a temporary `workflow_dispatch`/`pull_request`-triggered GitHub Actions job on `windows-latest` (commit `7b919b2` at the time of this note; the workflow itself is deleted once this note lands, per its own comment).

The script builds the real release binary (`.github/actions/build-native`, the same composite action `ci.yml`'s `Build (Windows)` job uses), launches `narration-utils.exe` with `APPDATA`/`LOCALAPPDATA` pointed at a scratch temp folder (so nothing here reads or writes a real per-user profile), and:

- confirms the window opens, using `Process.MainWindowHandle` and Win32 `IsWindowVisible`;
- drives real Win32 `SendInput` (not Playwright/CDP-synthesized input) for Ctrl+wheel, Ctrl+=/-/0, Alt+Left/Right and the mouse's XBUTTON1/XBUTTON2 - deliberately real OS-level input, because the whole question is what the OS message loop and WebView2 do with it *before* the page ever sees it, which a CDP-dispatched event bypasses entirely;
- tries to read the result back by connecting to WebView2's own Chrome DevTools Protocol port, set via the `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` environment variable (Microsoft's documented mechanism for adding Chromium command-line switches without an app code change).

**Run 1:** `--remote-debugging-port=9333` alone. The window opened (`launch: pass`), but the DevTools HTTP endpoint at `http://127.0.0.1:9333/json/list` never answered within 30 seconds (`devtools-port: fail`); every check depending on it was skipped.

**Run 2:** widened to `--remote-debugging-port=9333 --remote-debugging-address=127.0.0.1 --remote-allow-origins=*`, in case a newer Chromium's default binding or CORS policy for the DevTools endpoint was the blocker. Same result: window opened, DevTools port still never answered.

**Why, at Medium confidence:** `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` is documented as a fallback Microsoft's WebView2 Loader reads when the hosting app does not already supply its own `CoreWebView2EnvironmentOptions.AdditionalBrowserArguments` at environment creation. Wails v3 builds its own `CoreWebView2Environment` (this is exactly the mechanism `ZoomControlEnabled`, `mainWindowOptions()`'s own doc comment, and this PRD's Evidence section already lean on for the zoom-control trap); if it does not itself merge the environment variable's value in when it does, the env var is silently dropped. This spike did not read Wails v3's vendored source to confirm the browser-arguments code path the way the [global-hotkeys spike](global-hotkeys-while-reaper-has-focus.md) read its `global_shortcut_*.go` files line by line - doing that, or finding a different automation channel entirely (a debug-only host binding, or driving the OS accessibility tree instead of CDP), is real engineering investment beyond a "no product code" research phase, and is left for whoever picks up the mouse-button question again.

This container has no Windows session of its own (the same limitation every other spike in this repo notes); everything above came from two real `windows-latest` CI runs, not from a live desktop session, and the app's own smoke test (`apps/desktop/smoke.go`) explicitly assumes "a CI job cannot start it and look at a window" - true for its own non-interactive mode, but this spike shows an *interactive* launch works fine on the exact same class of runner.

## Not done, and why

- **The four numbered questions in the PRD's own Research Summary are still not directly observed**, for the reason above: the CDP channel that would have let a script read `devicePixelRatio`, `location.href` or the DOM never came up. This spike adds one new fact (CI can open the window) and one new limit (CI cannot currently read WebView2 state back through this particular mechanism); it does not raise or lower confidence on the zoom or mouse-button questions themselves beyond what the PRD's Evidence section already reasoned from source.
- **Touchpad pinch and a physical side-button mouse** were never in scope for a script: Win32 has no supported way to synthesize either. Per the PRD's own Phase 0 scope, these stay owner-pending on [#510](https://github.com/countrymanprime/narration-utils/issues/510).
- **Given the CDP channel's absence, the rest of the "not done" list from the PRD's Research Summary now also needs the owner's own machine**, not just their touchpad/mouse: Ctrl+wheel zoom's actual effect, the Ctrl+=/-/0 no-op, whether a zoom level survives a relaunch, and whether the mouse's back/forward buttons or Alt+Left/Right move anything at the OS layer. All four are quick for the owner to check by hand (the PRD's own Research Summary already says as much for two of them), and none of them blocks Phase 2, whose zoom mechanism (`Window.SetZoom`) was already settled independently by the owner (Q3, D29) before this phase ran.

## Recommendation

**Proceed to Phase 2 and 3 as planned.** Nothing this spike found contradicts the PRD's Proposed Solution, its Technical Approach, or Proposed ADR 0201's 100%-200% Windows zoom range; it only firms up that CI can drive the real packaged app interactively (useful precedent for a future phase that wants a live desktop check without the owner) and that reading state back over CDP is not currently available as a shortcut for that. Phase 2's own Verification already plans "a scripted Windows run: Ctrl+wheel moves the readout, the readout resets, 175% on a 1280 px window shows the drawer layout, and the range is clamped" - once Phase 2 ships the zoom binding, that verification can drive the same real UI controls this spike's ProjectPicker-only script could not reach (a project must be attached before the app's shell exists at all, per `apps/ui/src/App.tsx`'s `if (!data.projectFolder) return <ProjectPicker />;` gate), which sidesteps needing WebView2's own DevTools protocol at all.

**No Proposed ADR from this spike.** It settles a research question the PRD itself posed, and reverses nothing already decided (Q3/D29's `Window.SetZoom` mechanism stands).
