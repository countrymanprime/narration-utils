# Spike: can a global hotkey fire while REAPER has OS focus?

**Status: done, 2026-09-27.** Phase 12 of the [Input Commands and Pedals PRD](../prds/input-commands-and-pedals.prd.md) (tracking issue [#646](https://github.com/countrymanprime/narration-utils/issues/646)), lane A. This is research for the future companion-panel PRD, not a shipped feature — the PRD's own Phase 12 row says "Not MVP." Follows the format and rigor of [Phase 8's own spike note](web-midi-hid-webview-spike.md) for this PRD. A throwaway proof-of-concept lives at `apps/desktop/cmd/spike-globalhotkeys/main.go` on this spike's branch; it is not wired into the shipped binary and is not meant to ship (see [Method](#method)).

## The question

The PRD's Phase 12 row: "Can Wails v3 or the OS register a hotkey that fires while REAPER has focus, and at what cost (a Windows `RegisterHotKey` hook, macOS accessibility permission)? The keymap row (Phase 5, complete) is the source of truth either way." A narrator's footswitch or a dedicated hotkey should be able to reach the app even when REAPER — not this app — is the foreground window, for the future companion-panel feature.

## What it settles

| Question | Answer | Confidence | Unblocks |
| --- | --- | --- | --- |
| Can a hotkey this app registers fire while another process (REAPER) has OS focus? | **Yes, on every desktop platform Wails v3 targets** (Windows, macOS, Linux X11, Linux Wayland). Each mechanism is genuinely system-wide/OS-level, not app-scoped — that is its entire purpose, not an incidental side effect | High — read from the pinned dependency's actual source, not a secondhand report | A companion-panel phase can proceed without a platform-support spike of its own |
| Does Wails v3 already provide this, or would the app need to build it? | **Already provided.** The exact pinned version this app builds against (`github.com/wailsapp/wails/v3 v3.0.0-beta.25`, `apps/desktop/go.mod:8`) ships `app.GlobalShortcut` with `Register`, `Unregister`, `UnregisterAll`, `IsRegistered` and `GetAll` (`pkg/application/global_shortcut_manager.go`) | High — verified by reading and compiling against the vendored source of the pinned version itself | No new dependency, no vendored native code to write or maintain |
| What mechanism does each platform use? | Windows: Win32 `RegisterHotKey` against the app's hidden main-thread window, delivered as `WM_HOTKEY` on the same message loop the rest of the app already pumps. macOS: the Carbon Event Manager's `RegisterEventHotKey` (not a `CGEventTap` or an `NSEvent` global monitor). Linux X11: `XGrabKey` on the root window. Linux Wayland: the XDG Desktop Portal's `org.freedesktop.portal.GlobalShortcuts` interface over D-Bus | High for all four — each is a distinct `.go` file in the pinned source (`global_shortcut_windows.go`, `global_shortcut_darwin.go`, `global_shortcut_linux_x11.go`, `global_shortcut_linux_portal.go`) | Confirms the PRD's own guess (`RegisterHotKey`, macOS permission) was half right and refines the other half (see below) |
| Does it need elevated/unsandboxed rights, or a permission prompt? | **No, on Windows, macOS or Linux X11.** Windows: no admin/elevation. macOS: the pinned code's own comment states Carbon's `RegisterEventHotKey` — unlike a `CGEventTap` or an `NSEvent` global monitor — **does not require Accessibility permission**; this directly answers the PRD's named cost concern, and in the opposite direction the PRD's phrasing implied. Linux X11: no permission system exists to ask. **Linux Wayland is the one real exception:** the portal opens an interactive session, and the compositor — not the app — picks the final key combination, which may not match what was requested; only compositors that implement the portal (recent GNOME or KDE Plasma, per Wails' own example README) support it at all | High (Windows, macOS, X11); Medium (Wayland — this container has no compositor to test the portal dialog against, so its exact UX is read from Wails' own example README, not observed) | Removes the accessibility-permission cost the PRD flagged as a Windows-vs-macOS asymmetry; this app currently ships Windows-only anyway (see below), where the answer is unambiguous |
| What does it cost to build, beyond calling the API? | **On Windows: nothing beyond the API call.** The Windows backend (`global_shortcut_windows.go`) is pure Go over `syscall` — no cgo — and this proof-of-concept cross-compiles clean with the exact `CGO_ENABLED=0`/`GOOS=windows` invocation this app's own CI build already uses (verified, see [Method](#method)). macOS needs cgo and the Carbon framework; Linux X11 needs cgo and `libx11`; Linux Wayland needs `github.com/godbus/dbus/v5`, already an indirect dependency of this module today (`apps/desktop/go.mod`) | High | A Windows-only companion-panel phase adds no new build complexity at all |

## A cost the PRD didn't ask about: hotkey ownership is exclusive

Every one of these mechanisms (Windows, macOS, Linux X11) works by having the OS deliver the key **only** to the registering application — that is how a background app can see a key without a foreground window. If the app registers a combination REAPER's own keymap also binds, REAPER stops receiving that key at all while this app is running and holds the registration; there is no "both get it" mode. Whatever accelerator a future companion-panel phase picks must be checked against the narrator's REAPER keymap, not just against this app's own keymap (Phase 5's settings row). This is a design constraint for that PRD to carry, not something this spike can resolve — it doesn't know a given narrator's REAPER bindings.

## Method

This is desk research plus a compiled (not run) proof-of-concept, from a cloud container with no Windows, macOS or Linux desktop session, no REAPER installation, and no footswitch or keyboard hardware attached.

What makes this spike stronger than [Phase 8's own spike](web-midi-hid-webview-spike.md) for the same PRD: Phase 8 could not fetch its most authoritative sources (`learn.microsoft.com`, `webkit.org`) and relied on `WebSearch` synthesis and secondhand community reports for its lowest-confidence findings. This spike instead had `go mod download` access to `proxy.golang.org` (unlike the doc hosts Phase 8 hit, this host was not blocked — see [Not done, and why](#not-done-and-why)), so `github.com/wailsapp/wails/v3@v3.0.0-beta.25` — **the exact version pinned in `apps/desktop/go.mod`** — was fetched and read directly: `pkg/application/global_shortcut_manager.go`, `global_shortcut_windows.go`, `global_shortcut_darwin.go`, `global_shortcut_linux.go`, `global_shortcut_linux_x11.go`, `global_shortcut_linux_portal.go`, `global_shortcut_unsupported.go`, the shipped `examples/global-shortcuts/main.go` and its `README.md` (which the Wails maintainers themselves mark "Working" per platform, based on their own testing, not this spike's). This is primary-source evidence about this app's own pinned dependency, not a general claim about Wails or about Win32/Carbon/X11 from secondary sources.

The proof-of-concept (`apps/desktop/cmd/spike-globalhotkeys/main.go`) is a standalone `main` package — not wired into `cmd/narration-utils`, not built by any CI job — that calls `application.New` and `app.GlobalShortcut.Register("CmdOrCtrl+Shift+F13", …)`, the same call a real companion-panel binding would make. It was:
- Cross-compiled for `GOOS=windows GOARCH=amd64 CGO_ENABLED=0` — this app's only shipped target (`.github/workflows/ci.yml`, `.github/workflows/prerelease.yml`, `.github/workflows/security.yml` all run `runs-on: windows-latest`; there is no macOS or Linux build job) — using the same flags `scripts/release/wails-build.mjs` uses for the real binary. It built and `go vet`-ed clean.
- **Not run.** This container has no Windows session to launch the binary on, no REAPER process to bring to the foreground, and no way to press a physical or virtual key while it holds focus. Whether the callback actually fires while REAPER is foregrounded was not observed directly here; it rests on reading `global_shortcut_windows.go`'s use of `RegisterHotKey`/`WM_HOTKEY` (a well-documented, decades-stable Win32 mechanism whose entire purpose is exactly this) and on the Wails maintainers' own "Working" status for their example.

## Not done, and why

- **No live Windows, macOS or Linux desktop session, and no REAPER installation, in this container.** The proof-of-concept was compiled, not launched; nobody pressed a key while REAPER held focus. This is the same category of gap Phase 8 flagged for its own spike, for the same reason (no desktop environment here).
- **The Linux Wayland portal path was read, not exercised.** No compositor was available to actually see whether it prompts the user to choose a binding, what that dialog looks like, or whether the narrator's usual distro (unspecified) implements `org.freedesktop.portal.GlobalShortcuts` at all.
- **The macOS hardware-key-code table's non-QWERTY caveat was read, not tested.** `global_shortcut_darwin.go`'s own comment notes its `macKeyCodes` table assumes a standard ANSI/QWERTY physical layout; this spike has no non-QWERTY macOS keyboard to confirm the practical effect.
- Unlike Phase 8, no host was blocked by the network egress proxy for this spike's core question — `github.com`, `proxy.golang.org` (via `go mod download`) and general web search were all reachable, which is why this note's confidence is High rather than Low/Medium on most rows.

## Recommendation

**Yes, a follow-up phase in the future companion-panel PRD is worth building — on Windows, this app's only currently-shipped target.** The mechanism already exists in the exact pinned Wails version, costs nothing extra to build (no cgo, no elevation, no permission dialog, no new dependency), and answers the benchmark's Booth UX need directly: a footswitch or hotkey that reaches the app while REAPER holds focus.

Concretely, for whoever writes that PRD:
1. Reuse `app.GlobalShortcut` from `apps/desktop/wailsapp.go`, matching this codebase's existing "every call into Wails goes through this one file" pattern ([ADR 0200](../adr/0200-the-desktop-shell-runs-on-wails-v3-beta-pinned-at-v3-0-0-beta-25.md)) — the same file that already wraps `application.Get()` for `emitEvent`, dialogs and the window.
2. Feed a fired global shortcut into the same `apps/ui/src/input/` command registry (Phase 1) that keyboard, MIDI and HID presses already go through, as a host-originated event, rather than a second dispatch path. The keymap row (Phase 5, complete) already stores the binding; nothing about this mechanism changes what that row's shape needs to be.
3. Check any chosen accelerator against the narrator's REAPER keymap before shipping a default, per the [ownership caveat](#a-cost-the-prd-didnt-ask-about-hotkey-ownership-is-exclusive) above — an OS-level grab is exclusive, not additive.
4. Treat macOS and Linux support as available-if-needed rather than blocking: the same API covers them (Carbon on macOS needs no Accessibility permission either; Linux needs the X11 or Wayland-portal path already described), but this app ships Windows-only today, so there is no forcing reason to spend companion-panel budget verifying platforms this app does not yet build for.
5. **A real Windows machine must still confirm the live behaviour** (see [For #510](#for-510-owner-or-hardware-needed)) before that phase calls itself done — this spike raises confidence from "unknown" to "expected to work, unverified live," not to "verified."

**No Proposed ADR from this spike.** It doesn't reverse any existing decision (ADR 0361's registry design already treats device sources as pluggable, and this fits that shape); it only informs a PRD that doesn't exist yet, the same precedent [Phase 8's spike](web-midi-hid-webview-spike.md#recommendations) set for this same PRD.
