# REAPER spike S7: fixed item lanes through the API

**Status: done, 2026-09-23. Everything below was observed in REAPER 7.80/x64 on Windows; a different version may differ.** Spike S7 of the [REAPER automation research](reaper-automation-surface.md) (section 3, section 9 item 8) and phase 24 of [reaper-automation-follow-through.prd.md](../prds/reaper-automation-follow-through.prd.md). It ran unattended in a real REAPER under owner decision D3 (isolated resource directory, a scratch project only). It checks what phase 25 (retakes as fixed lanes) may assume, against the take-review decisions it depends on: a candidate reading becomes a take on the target item through `AddTakeToMediaItem`, its provenance lives in take `P_EXT` ([ADR 0098](../adr/0098-take-provenance-in-take-extension-data-extends-adr-0026.md)), and the app never sets the active take.

## What it settles

| Question | Answer |
| --- | --- |
| Does `I_FREEMODE=2` turn fixed lanes on, and is `UpdateTimeline()` needed? | Yes, it returns true and reads back 2 at once. `UpdateTimeline()` made no difference to any value read back; the spike calls it after every change because the docs ask for it. **But the API alone leaves the track half-set-up:** it writes `ITEMLANES 1` with items at `YPOS 0 0.5 2` (half the track height), and when the project is reopened REAPER reads that as **two** lanes, the second empty (`I_NUMFIXEDLANES` 1 before the save, 2 after; a re-save writes `ITEMLANES 2`). REAPER's own action "Track properties: Set fixed item lanes" (42431) writes `YPOS 0 1 2` and reopens as one lane, and so does the API followed by `I_NUMFIXEDLANES=1`. |
| Does turning lanes on spread overlapping items over lanes? | No, neither through the API nor through action 42431: two overlapping reads stay overlapping in lane 0, both playing. Only the "convert takes to lanes" actions move anything into other lanes, and only takes. |
| `I_FIXEDLANE` and `I_NUMFIXEDLANES` | A new item on a lane track lands in lane 0. Setting `I_FIXEDLANE=1` moves it and **grows the track to 2 lanes by itself**; setting it to 6 grows the track to 7. The track never shrinks when the item moves back: 7 lanes stayed 7 (six of them empty). `I_NUMFIXEDLANES` can also be set directly (3 read back as 3). |
| What does lane play state look like, and can the API set it? | Track `C_LANEPLAYS:N` is 0 (silent), 1 (plays exclusively) or 2 (plays together with others). With every lane playing, every lane reads 2 and `C_ALLLANESPLAY` reads 1. Setting `C_LANEPLAYS:1=1` silenced every other lane (they read 0, `C_ALLLANESPLAY` 2), and then `C_LANEPLAYS:2=2` added lane 2 alongside it (1 read 2). Setting the only playing lane to 0 left **no lane playing** (`C_ALLLANESPLAY` 0), silently. Setting `C_ALLLANESPLAY=1` turned every lane back on. The item-level `C_LANEPLAYS` reads its lane's state. **The docs call it read-only, but setting it to 1 on an item in lane 2 did make lane 2 the only lane playing**; nothing should rely on that. |
| Undo | Every API change wrapped in `Undo_BeginBlock2`/`Undo_EndBlock2` was exactly one undo step, and so was every action: enabling lanes, a play-state change (REAPER's own lane actions label theirs "Change lane play state"), converting takes to lanes or back ("Set/unset track fixed lanes"), exploding takes ("Explode takes to fixed lanes"), making a comp lane ("Set comping lane") and adding a comp area ("Add comp areas for selected items"). Redo restored each one exactly. A track's Lua pointer stayed valid across undo; item pointers must still be looked up again by GUID, as the take-review spike found. |
| Lane names | `P_LANENAME:N` sets and reads back through `GetSetMediaTrackInfo_String`, and is saved as `LANENAME "Retake 1" "Retake 2" ...`. Unnamed lanes read back as empty or as their number ("1", "2", ...) depending on how the lanes were made, so only a name set through `P_LANENAME` means anything. |
| Showing one lane | "Show/play only one fixed item lane" (43098) set `C_LANESCOLLAPSED` to 1 and `B_FIXEDLANE_HIDDEN` to 1 on the items in the lanes not playing. |
| Takes on a lane track (the take-review path) | `AddTakeToMediaItem` still works on an item in a lane: the item gets a third take, the active take stays where it was, no lane is added. **Takes and lanes are two separate ways to hold retakes, and a lane item can also hold takes.** |
| Converting takes to lanes | "Set fixed lanes (convert takes to lanes)" (42661) and "Explode takes on selected tracks to fixed lanes" (42635) did the same thing to a two-take item: one item per take, in take order (take 0 in lane 0). The item in lane 0 keeps the original item GUID; each other lane gets a new item with a new GUID. **The item-level line id (`P_EXT:narration_utils_line_id`) is copied onto every lane item**, and each take's `P_EXT` provenance moves with its take. **Lane 0 plays, whichever take was active:** with the candidate made active first (`I_CURTAKE=1`), after the conversion lane 0 (the original target) was the one playing. One undo step undoes the whole conversion. |
| Converting lanes back to takes | "Unset ... (convert fixed lanes to takes)" (42662) on three retakes with lane 1 playing gave one item (the lane 0 item's GUID) with three takes in lane order, **the playing lane's take active** (`I_CURTAKE=1`), and every take's `P_EXT` provenance kept. The other items' GUIDs are gone. |
| Turning lanes off by the API | `I_FREEMODE=0` on a track with three retakes in three lanes put all three back in one lane, **all three playing at once**: the lane play state is lost and the result is audibly different (three reads mixed together). One undo restores the lanes and the play state. |
| Comp lanes | "Comp into new empty lane" (42797) inserted a lane at the top named "C1", shifted every other lane down by one (`I_FIXEDLANE` 0,1,2 became 1,2,3) and made the empty comp lane the only one playing: **the track goes silent where there is no comp area yet**. "Add comp areas for selected items" (42652) on one retake put a **new item** in the comp lane: a copy of that retake with its own GUID and **the same item-level line id**. "Delete comp areas" and "Turn off comping" left that copy and the comp lane in place. |
| What the `.rpp` records | Track: `FREEMODE 2` (absent when lanes are off), `ITEMLANES <n>`, `LANESOLO <bitmask> ...` (bit N set means lane N plays: `4` is lane 2 alone; all bits set except bit 1 is `4294967293`), `LANEREC`, `LANENAME ...`, and `LINKEDLANE <start> <end> <source lane> 0 -1 <fade in> <fade out>` per comp area (the field meanings after the source lane are inferred, not verified). Item: **there is no lane number**, only `YPOS <top> <height> 2`, the item's top and height as fractions of the track (`YPOS 0.5 0.25 2` is lane 2 of 4). Everything above survives a save and reopen, except the API-only enable in the first row. |

## Recommendation for phase 25 (retakes as fixed lanes)

Phase 25 is **feasible, in a narrower shape than "choose the good lane per line"**, recorded as [ADR 0147](../adr/0147-retakes-on-fixed-lanes-are-chosen-by-lane-play-state-and-the-app-never-converts-takes-and-lanes.md) (Proposed):

1. **The narrator's pick is a lane play change, nothing else.** Choosing retake N sets `C_LANEPLAYS:N=1` in one undo block: every other lane goes silent, no item or take is moved, deleted, copied or re-activated, and one undo puts it back. It needs a track the narrator already put in fixed-lane mode, since the app never sets `I_FREEMODE`.
2. **The app never converts between takes and lanes, turns lanes on or off, or builds comps.** Each conversion changes what plays (takes to lanes plays lane 0, not the active take; lanes off by the API plays every retake at once) or copies the line id onto new items (conversions and comp areas). Those stay the narrator's own REAPER actions. That matches the take-review rule that the app never sets the active take: in both, the narrator decides what is heard.
3. **A line id no longer names one item on a lane track.** Every retake of a line, and any comp copy, carries the same `narration_utils_line_id`. Phase 25 has to name a retake by line id plus item GUID (or line id plus lane), and treat "the take that plays" as "the item whose lane plays". Split and duplicated items already share a line id ([ADR 0026](../adr/0026-manuscript-line-identity-in-item-extension-data.md), checklist step 6), but on a lane track it is the normal case, so anything that goes from a line id to one item has to choose among them by play state.
4. **The static reader has to learn lanes first.** `apps/desktop/internal/tracks` reads a lane track as overlapping items (three retakes at the same position, all "playable") because it reads neither `YPOS` nor `ITEMLANES` nor `LANESOLO`. Before any UI shows retakes by lane, the parser needs the lane (from `YPOS` and `ITEMLANES`) and whether it plays (from `LANESOLO`). The new fixture pins today's lane-blind reading so that change is made on purpose.
5. **Takes stay the take-review mechanism.** Take review (phase 6 of its PRD) adds a candidate as a take on the target item, and that still works on a lane track. Retakes as lanes is a second, separate way retakes reach the timeline: fixed-lane recording, the narrator's own. Phase 25 reads that, and adds no new way to make retakes.

Phase 25's success signal was "TBD - needs research after S7": with this note it can be "the narrator picks a lane for a line and only that lane plays; one undo restores the previous play state; nothing else in the project changes."

## Method

- **Machine and build.** Windows 11, REAPER 7.80/x64 (`<REAPER_PROJECT 0.1 "7.80/win64" ...>` in the saved file), the same installation S0, S5 and the take-review spike used.
- **Isolation.** `reaper.exe -cfgfile <temp>\reaper.ini -nosplash -newinst -noactivate <script>`, through the existing [`run-reaper.ps1`](../../integrations/reaper/spikes/run-reaper.ps1) (unchanged): `-Cfg` and `-Out` under the temp folder, the script asserts REAPER's resource path is the scratch `-Cfg` folder, `Audio_Quit()` runs first and `Audio_IsRunning() == 0` is asserted. Nothing was armed, recorded or played. No project was opened except the script's own scratch project, and no file of the owner's REAPER setup or projects was read or written; only the REAPER process the driver started was closed, and none was left running.
- **Why no copy of `Challenges_001.rpp`.** Lane behaviour does not depend on which project it runs in, and a scratch project with synthetic tones ([`make_media.py`](../../integrations/reaper/spikes/make_media.py)) makes every position, lane and play state exact and the saved file small and shareable. The same choice as S5 and the take-review spike.
- **Action IDs.** A first pass listed every action in the Main section whose name mentions lanes or comps (about 210 in 7.80, ruler-lane actions included). The script names each action it runs with both its ID and its expected text and stops if the text differs, so a renumbered action cannot run something else.
- **Script.** [`integrations/reaper/spikes/spike_s7_fixed_lanes.lua`](../../integrations/reaper/spikes/spike_s7_fixed_lanes.lua): sections A to H, one track per case, a dump of every lane value on the track and its items after each step, and the lane lines of the track's state chunk. Three runs; the first two shaped the cases (the second added the action-based enable, the active-candidate conversion, lanes back to takes, and a comp area left in place), and the third is the recorded one: [`results/fixed-lanes-report.txt`](../../integrations/reaper/spikes/results/fixed-lanes-report.txt).
- **Fixtures.** [`fixed-lanes.rpp`](../../apps/desktop/internal/tracks/testdata/reaper/fixed-lanes.rpp) is the project exactly as REAPER saved it at the end of the run (14 tracks, one per case, relative media paths). [`fixed-lanes-resaved.rpp`](../../apps/desktop/internal/tracks/testdata/reaper/fixed-lanes-resaved.rpp) is the same project reopened and saved again, which shows the phantom lane (`ITEMLANES 1` becoming `ITEMLANES 2` on the tracks enabled by the API alone); its absolute media paths are scrubbed as the fixture README describes. `apps/desktop/internal/tracks/reaper_fixed_lanes_test.go` pins what the parser makes of them.

## Pending (needs audio hardware or the owner)

- **Recording into lanes.** What REAPER does when the narrator records on a fixed-lane track (a new lane per pass, which lane plays, the "new recording adds lanes" options 43151 to 43153, auto-comping, `LANEREC`) needs an armed input and a real recording, so it was not run. It is the main way retakes would reach lanes in practice, so phase 25 should check it with the owner before relying on "one lane per pass".
- **What the narrator hears.** Play state was read back, never listened to: that only lane N is audible after `C_LANEPLAYS:N=1` is REAPER's documented meaning, not something this run heard.
- **Mouse-driven comping** (razor-edit comp areas, "comp area at mouse" actions) was not exercised; the non-mouse actions above cover what the file records.
