# Phase 14 conditional evaluation: static `.rpp` read of line IDs

**Status: done, 2026-09-22. No code was launched or changed by this evaluation; it is a desk check of the existing codebase on the `reconcile-rf-el` tip (`hostAPIVersion` 19).** Phase 14 of [reaper-automation-follow-through.prd.md](../prds/reaper-automation-follow-through.prd.md) and its Open Question 9 are explicitly conditional: "build it only if the S0 spike shows a stable, parseable serialisation *and* a standalone consumer needs it; otherwise never, always read through `read_line_ids`." [Spike S0](reaper-spike-s0-item-extension-data.md) already settled the first half (yes, a stable `key value` `<EXTI`/`<EXT` block, four value forms, parseable without REAPER). This note settles the second half.

## Question

Does any standalone (no running REAPER, no bridge client) consumer in this codebase genuinely need to read manuscript line identity from a saved `.rpp` file today?

## What was checked

- **`apps/desktop/internal/evidence`'s staleness evaluator** (`staleness.go`, `fingerprint.go`, Phase 6 of `analysis-evidence-ledger.prd.md`). `ComputeItemFingerprint` and the evaluator's item facts hash `item.GUID`, position, length, mute and active-take index only (`fingerprint.go:94-102`). Neither file reads `Item.Ext` or any `narration_utils_line_*` key. The evaluator answers "is an analysis record current for this chapter's items", a question about item edits, not manuscript-line identity.
- **`apps/desktop/internal/tracks`, the parser superset itself.** `extension.go`'s `extensionData` already parses `<EXTI`/`<EXT` blocks into `Item.Ext` / `Take.Ext` (`map[string]string`, all four S0 value forms) as part of the parser superset built for the evidence ledger's fingerprinting and take-review's future provenance needs — not for line identity specifically. `Item.Ext` is tagged `json:"-"`: nothing serializes it to the UI today, and no production code (`grep -rn` for `.Ext` outside `_test.go` in `internal/tracks` and `internal/evidence`) reads a `narration_utils_line_id` or `narration_utils_line_text` key from it. So the low-level building block Phase 14 would need already exists as a side effect of other phases; what's missing is only a purpose-built accessor and a consumer, and there is no consumer.
- **`apps/desktop/internal/lineidentity`** (Phase 6/7, the actual line-identity service). `Stamp`/`Read`/`Drain` all return early when `s.bridge == nil` (`service.go:79,129,152`) — this service is REAPER-launched only by design; it does not fall back to a static read, and nothing asked it to.
- **`apps/desktop/tracks.go`'s `tracksList` binding**, the one standalone (no-bridge-required) consumer of the `tracks` package. It calls `tracks.Parse` directly from the project folder — genuinely standalone — but returns `tracks.Project`/`Item` through the existing wire contract, which does not include `Ext` (`json:"-"`). The Tracks page UI (`apps/ui/src/components/tracks/*`) has no line-identity display; `LinkChaptersDialog.tsx` drives `Stamp`/`Read` through the bridge-backed bindings, not a static parse.
- **`docs/architecture/manuscript-line-identity.md`'s own "Later phases" list** (item 3) already calls the static read "(optional)" and says explicitly: "Until then use `read_line_ids`."
- **Sibling PRDs that touch line identity or per-item extension data**: `take-review-pickups-duplicates-take-intelligence.prd.md` Q6 is answered (B) — that PRD does **not** require manuscript line-identity stamps; spans come from alignment at analysis time. `teleprompter-manuscript-integration.prd.md` explicitly excludes writing or needing line IDs ("resume only reads; line-identity stamping stays a separate initiative") and its chapter-to-track matcher reads `tracks` for `SOFFS`/`PLAYRATE`/active-take, not `Ext`. `native-recording-suite.prd.md` and `audacity-integration.prd.md` mention line identity only to say it's REAPER-only / out of scope for them. No PRD names a flow that runs with the app launched standalone (outside REAPER) and needs to show or use a manuscript line ID.

## Answer

**No standalone consumer needs it.** Every place line identity is read today goes through the bridge (`read_line_ids`), and every standalone (`tracksList`) code path that already exercises the very same `.rpp` parser deliberately stops short of exposing `Ext` to anything. No other PRD's phase table names a flow that would consume it standalone.

Per the PRD's own recommendation on Open Question 9 ("(a)... otherwise never, always read through `read_line_ids`"), this means: **do not build the static parser now.** Building an unused accessor and UI-facing consumer would be speculative generality against a condition the PRD itself says not to build ahead of.

## Decision and unblocks

Phase 14 is marked `complete` in the phase table as "evaluated, condition not met" rather than left `pending` indefinitely — the condition is a real gate that was actually evaluated, not skipped work. Open Question 9 is ticked "evaluated, not built: no standalone consumer exists yet." If a future PRD or phase introduces a standalone flow that needs line identity (for example, a Home-page or offline preview that shows stamped lines without the app being launched from REAPER), re-open this question: the S0 half of the condition remains satisfied, the `tracks` parser already carries the necessary `Ext` data internally, and `extensionData`'s four-value-form handling in `apps/desktop/internal/tracks/extension.go` is exactly what a future accessor (`Item.Ext["narration_utils_line_id"]` / `["narration_utils_line_text"]`) would build on — this note is the record of why it wasn't built now, not a statement that it can't be.
